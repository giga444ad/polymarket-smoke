# Сессия 16 — модуль бэктеста как полноценный Nest-модуль (Часть 2 плана)

Реализована Часть 2 `BACKTEST-PLAN.md` (Часть 1 — параллельное хранение
тиков — была сделана в Сессии 15). Бэктест теперь живёт внутри основного
NestJS-приложения (`BacktestModule`, `POST /backtest/run`) — как и просил
пользователь, никакого отдельного скрипта: один и тот же модульный Nest
держит и торговлю, и аналитику, и теперь бэктест.

## Главный принцип (дословное требование пользователя, см. BACKTEST-PLAN.md)

> Бэктест должен быть по такой же логике, как и сейчас вот реальный
> on-time флоу — НЕ отдельная "модель", реализующая ту же идею заново, а
> честный повтор существующего кода.

Сделано буквально: логика принятия решения о входе (`evaluateEntryGate`,
все 5 фильтров — базовый ATR-гейт + 4 доп. фильтра Сессии 13) вынесена из
`TradingService` в отдельный DI-независимый класс `EntryGateEngine`
(`src/trading/entry-gate.engine.ts`) и переиспользуется дословно и в live,
и в бэктесте. Аналогично вынесены `computeTier`/`pickFavorite`/`roundToTick`/
`limitOrderTargetUsd` в чистые функции `src/trading/market-decision.util.ts`.
Симуляция исполнения по стакану переиспользует ту же `walkAsksForFill`
(`book-fill.util.ts`), что и live-путь.

`TradingService` при этом ведёт себя ИДЕНТИЧНО прежнему — рефакторинг чисто
механический (логика перемещена, не переписана), все 20 тестов
`scripts/verify-trading-logic.ts` и все тесты `verify-price-feed.ts`/
`verify-tick-recorder.ts` проходят без единой правки в самих тестах.

## Новые файлы

- `src/trading/entry-gate.engine.ts` — `EntryGateEngine`, `IPriceSource`,
  `IClock`, `GateContext`, `EntryDiagnostics` (перенесено из
  `trading.service.ts`, логика не менялась).
- `src/trading/market-decision.util.ts` — `computeTier`/`pickFavorite`/
  `roundToTick`/`limitOrderTargetUsd` как чистые функции.
- `src/backtest/replay-clock.ts` — `ReplayClock implements IClock`,
  виртуальные часы (BACKTEST-PLAN.md, п.2.2).
- `src/backtest/replay-price-source.ts` — `ReplayPriceSource implements
  IPriceSource`: реплеит `price_ticks` через ТУ ЖЕ бухгалтерию свечей/ATR/
  recentTicks-буфера, что и `PriceFeedService` (та же формула ATR — целая
  свеча = целое окно потока, тот же fail-closed при недостатке истории).
- `src/backtest/backtest-runner.service.ts` — `BacktestRunnerService`, ядро:
  группирует `polymarket_price_ticks` в окна по `slug`, для каждого окна
  реплеит вход РОВНО по той же последовательности правил, что и
  `onBookUpdate`/`tryMarketBuy`/`placeOrReplaceLimit` в `TradingService`
  (резюм-лимитка -> Правило A -> Правило B, с той же перепроверкой гейта на
  момент исполнения лимитки — фикс Сессии 10).
- `src/backtest/backtest.controller.ts` — `POST /backtest/run`.
- `src/backtest/backtest.module.ts` — регистрирует контроллер+сервис,
  подключается к тем же таблицам через общий TypeORM-коннект приложения (без
  отдельного подключения к БД, в отличие от `tick-recorder.ts` — бэктест
  только читает).
- `src/backtest/backtest.types.ts` — DTO запроса/ответа.
- `public/backtest.html` — минимальная статическая страница (форма
  параметров + таблица сделок), как и просил план ("не полноценный
  фронтенд-проект, а рабочий инструмент"). Доступна как `/backtest.html`
  при `IS_STATIC=true`, отдельно от основного дашборда `index.html`.
- `scripts/verify-backtest.ts` — ad-hoc тест на фейковых in-memory
  репозиториях (без реальной БД), проверяет, что весь пайплайн (загрузка
  тиков -> прогрев ATR -> референс окна -> вход -> исход) не падает и даёт
  ожидаемый результат на синтетическом сценарии.

## API

`POST /backtest/run`
```json
{
  "streamKey": "btc-updown-5m",
  "from": "2026-09-01T00:00:00Z",
  "to": "2026-09-08T00:00:00Z",
  "envOverrides": { "MIN_DISTANCE_ATR_RATIO": "2", "EXPECTED_MOVE_FILTER_ENABLED": "true" },
  "assumedMinOrderSize": 5
}
```
`envOverrides` принимает ЛЮБЫЕ из тех же ENV-ключей, что и боевой
`TradingService` (гейт/фильтры/тиры/окно входа/пороги маркет-тейка) — не
заданные явно берут значение из текущего `.env` процесса. Это прямой ответ
на "я пробую разные настройки env" — теперь их можно проверить на истории
одним HTTP-запросом, без перезапуска бота и без ожидания следующего реального
окна.

Данные берутся ТОЛЬКО из уже накопленной истории (`price_ticks`/
`polymarket_price_ticks`) — никаких сетевых запросов к Gamma/CLOB.

## Честно задокументированные ограничения (в каждом ответе API, поле `limitations`)

Это НЕ обещанная в исходном плане идеальная "честная" симуляция по ряду
причин, связанных с тем, что реально сохраняет `tick-recorder` (Сессия 15) —
план прямо требовал не подменять недостаток данных тихой интерполяцией, а
показывать это явно:

1. **Нет полной глубины стакана.** `polymarket_price_ticks` хранит только
   лучшие bid/ask (см. `polymarket-price-tick.entity.ts` — так было решено
   в Сессии 15), не весь стакан. Исполнение поэтому симулируется как один
   уровень "лучшая цена, условно неограниченный объём" — та же функция
   `walkAsksForFill`, что и в live, но с одним синтетическим уровнем.
   Следствие: `MIN_FILL_RATIO`/частичные филлы в бэктесте не воспроизводятся
   содержательно (`fillRatio` всегда 1.0 при исполнении). Если это важно —
   следующий шаг: доработать `tick-recorder.ts` до записи полного стакана
   (уровни, не только top-of-book).
2. **`minOrderSize` не сохранялся** — используется предположение
   (`assumedMinOrderSize`, по умолчанию 5), не реальное значение биржи на тот
   момент.
3. **Один источник цены за прогон.** `price_ticks` пишет chainlink/binance/
   bybit независимо и параллельно (не "один активный с фолбэком", как живой
   `PriceFeedService`, см. Сессию 9) — бэктест реплеит ОДИН источник целиком
   по приоритету (`providerPriority`, по умолчанию chainlink), переключения
   провайдера внутри окна не воспроизводятся.
4. **Официальный исход Gamma не сохранялся.** win/loss определяется
   приближённо: цена по фиду на момент официального закрытия окна
   относительно референса (`impliedWinnerSide`) — тот же методологический
   зазор, что уже описан в `CONTEXT.md` (Сессии 10-11) как источник части
   дисперсии на живых сливах. В бэктесте это не устранено, а прозрачно
   перенесено в ответ на каждую сделку.
5. **`closesAtMs`/`windowStartMs` — приближение.** `active_windows` хранит
   только ТЕКУЩИЙ указатель (перезаписывается/чистится), истории окон там
   нет — граница окна в бэктесте берётся как момент последнего
   зафиксированного `polymarket_price_ticks`-снимка для данного `slug` минус
   длительность окна. На практике recorder слушает почти до самого закрытия
   (см. `TICK_RECORDER_WINDOW_POLL_MS`/`TICK_RECORDER_PM_SNAPSHOT_MS`), так
   что расхождение — не больше секунды-другой, но это не точный официальный
   таймстемп.
6. **Реинвест-прогрессия НЕ реализована.** Каждое окно в этой версии
   считается с фиксированным `baseStake` потока — компаундинг между окнами
   (как в live `Attempt.currentStake`) сознательно отложен на следующий шаг
   (см. BACKTEST-PLAN.md п.2.5 — это итеративная задача, не однодневная).

## Проверено

- `npx tsc --noEmit -p tsconfig.json` — чисто.
- `npx nest build` — чисто.
- `npx tsx scripts/verify-trading-logic.ts` — все 20 тестов зелёные
  (без единой правки в самом тесте — подтверждает, что рефакторинг
  `TradingService` не изменил поведение).
- `npx tsx scripts/verify-price-feed.ts` / `verify-tick-recorder.ts` — без
  изменений, всё так же зелёное.
- `npx tsx scripts/verify-backtest.ts` — новый тест, зелёный (синтетический
  сценарий: прогретый ATR + уверенный уход цены -> маркет-тейк вход -> исход).
