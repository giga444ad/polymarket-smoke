# Auth / деплой-архитектура (4 бэкенда + 1 фронтенд)

## Идея одним абзацем

Один и тот же код (этот репозиторий) деплоится 4 раза (BTC/SOL/ETH/DOGE — как
и сейчас), но только на ОДНОМ из них выставляется `IS_MAIN=true` и публичный
домен `api.axiomis.ru`. Только этот сервис хранит `users`, знает `JWT_SECRET`
и выдаёт токены. Остальные три работают с `IS_MAIN=false`: пользователей у
них нет вообще, а входящий JWT они не проверяют сами — ходят с ним на
`IS_MAIN`-сервис (`GET /api/auth/validate`) и кэшируют результат на
`AUTH_REMOTE_CACHE_TTL_MS` (по умолчанию 30с), чтобы не превращать каждый
запрос дашборда в 2 сетевых похода. Архитектуру "4 сервиса + 4 БД" трогать не
пришлось — авторизация — это отдельный горизонтальный слой поверх неё.

## Почему так, а не иначе

- **Общий JWT_SECRET на всех 4** был бы проще (все проверяют локально), но
  тогда секрет размножен на 4 инстанса — компрометация любого из трёх
  "второстепенных" сервисов утекает секрет, которым подписывается доступ к
  главному. Текущая схема держит секрет ровно в одном месте.
- **Полный поход в main на КАЖДЫЙ запрос** was too slow/fragile (падение
  main = падение всех). Поэтому — кэш на 30с: компромисс между "секунда
  простоя main не должна валить всё" и "отозванный токен не должен жить
  часами на периферии".
- Не стали городить общую БД пользователей поверх 4 отдельных Postgres —
  тоже усложнение архитектуры, которого просили избежать.

## Что нужно сделать при деплое

1. На сервисе, который станет главным (домен `api.axiomis.ru`):
   - `IS_MAIN=true`
   - `JWT_SECRET=$(openssl rand -hex 32)`
   - `CORS_ORIGIN=https://<домен-фронтенда-на-vercel>` (можно перечислить
     несколько через запятую — прод + preview-домены Vercel)
2. На трёх остальных:
   - `IS_MAIN=false` (или просто не задавать — дефолт `false`)
   - `MAIN_VALIDATE_URL=https://api.axiomis.ru`
   - `JWT_SECRET` НЕ заводить вообще — он им не нужен.
   - `CORS_ORIGIN` — тот же домен фронтенда (дашборд ходит на все 4 базовых
     URL напрямую с одним и тем же токеном).
3. На всех 4: `THROTTLE_LIMIT`/`THROTTLE_TTL_MS` при желании подстроить под
   реальный трафик дашборда (дефолт: 120 запросов/минуту с IP).
4. Завести пользователей вручную на IS_MAIN-сервисе (там же таблица `users`):
   ```
   npx tsx scripts/create-user.ts alice "длинный-пароль-12+" admin
   npx tsx scripts/create-user.ts bob   "другой-длинный-пароль" viewer
   ```
   Роли: `admin` — видит всё + может `close-early` и `POST /backtest/run`;
   `viewer` — только чтение `/analytics/*`.

## Что теперь закрыто (сводка ревью)

- Все ручки, кроме `GET /api/health` и (только на IS_MAIN) `POST
  /api/auth/login`, требуют валидный `Authorization: Bearer <jwt>`.
- `close-early` и `backtest/run` (единственные мутирующие/тяжёлые ручки)
  — только роль `admin`.
- `CORS` был `origin: '*'` + `credentials: true` (дыра) — теперь белый
  список доменов из `CORS_ORIGIN`, credentials выключены (токен передаётся
  заголовком, не куки — куки тут не нужны).
- Добавлен `helmet` (security-заголовки) и глобальный `ThrottlerGuard`
  (rate-limit по IP), плюс отдельный, более жёсткий лимит на
  `/auth/login` (5 попыток/60с) — защита от перебора пароля.
- `ValidationPipe({ whitelist: true, forbidNonWhitelisted: true })` глобально
  — тело запроса, не описанное DTO, отклоняется, а не тихо игнорируется.
- Регистрации нет и не будет — пользователи заводятся только через
  `scripts/create-user.ts` (bcrypt, 12 раундов), пароль руками в БД никогда
  не хранится в открытом виде.
- Ошибка логина не палит, залогинена ли учётка ("неверный пароль" vs
  "юзера нет" — один и тот же ответ).
- Все ручки теперь под общим префиксом `/api` (`app.setGlobalPrefix('api')`)
  — совпадает с `api.axiomis.ru/api` из задачи.
- Старый монолитный `index.html`/`public/*.html` (React без сборки, инлайн в
  бэкенде) убран из бэкенда — фронтенд теперь отдельный проект, см.
  `../axiomis-dashboard`. `ServeStaticModule`/`IS_STATIC` оставлены только как
  легаси-путь для локальной отладки, в проде не используются.

## Не забыть перед деплоем

- `TYPEORM_SYNC` — на боевых средах лучше `false` + нормальные миграции
  (сейчас `synchronize` по умолчанию `true`, что уже было в проекте и не
  относится к auth-ревью, но стоит помнить: `synchronize: true` в проде на
  таблице с паролями — плохая идея при любых будущих правках схемы).
- `npm run user:create` работает только там, где реально есть таблица
  `users`, т.е. на IS_MAIN. На остальных трёх `User`-сущность в
  `TypeOrmModule` тоже зарегистрирована (иначе не соберётся общий
  `entities: [...]` список), но таблица там просто не используется для
  логина — это не дыра, т.к. `AuthController`/`AuthService` там вообще не
  регистрируются (`IS_MAIN=false` ветка `AuthModule.register()`).
