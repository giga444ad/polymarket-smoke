## Как устроена система (карта)

- **Модель:** независимые «потоки» (актив × таймфрейм), у каждого своя
  state-машина и реинвест-прогрессия (`Attempt`: шаг/стейк/профит).
- **Циклы:**
  - `discoveryTick` (~1.5с) — открывает окно, если поток `enabled` и предыдущий
    шаг зарезолвлен (гейт `block`/`pre_resolve`).
  - `onBookUpdate` (WS) — вход в последние N сек: Правило A маркет-тейк (FAK,
    VWAP, ≥`minFillRatio`), иначе Правило B лимитка-фолбэк по тирам T1/T2/T3.
  - `finalizeMarket` (таймер закрытия) — close-диагностика / проверка статуса
    лимитки, снятие resting.
  - `resolvePendingMarkets` (~10с) — Gamma → win/loss → прогрессия/сброс + клейм.
  - `RedeemService` — клейм через relayer; `BalanceService` — гейт по балансу.
- **Снимки** `attemptId/stake/reference` фиксируются на открытии окна (закрывает
  гонки с резолвером). Это правильно, трогать не нужно.

## 🔴 Высокий риск (реальные деньги)

### 1. Маркет-путь без in-flight-гарда → двойная покупка при латенси
- **Где:** `src/trading/trading.service.ts:1183` (вызов `void this.tryMarketBuy`).
- **Суть:** защищён только троттлом 800мс; `positioned=true` ставится ПОСЛЕ
  await'а ордера. Если `placeMarketBuy` дольше 800мс — следующий тик пройдёт
  гейт и выстрелит второй реальный FAK на ту же сторону = двойной стейк.
- **Фикс:** добавить `marketInFlight: boolean` в `MarketState`, гард в начале
  `tryMarketBuy` (или перед `void`-вызовом) + сброс в `finally`. Симметрично
  тому, что уже сделано на лимит-пути (`limitInFlight`).

### 2. Ненадёжное определение факта исполнения GTD-лимитки → позиция теряется
- **Где:** `src/trading/trading.service.ts:1540` (`getOrderStatus` в `finalizeMarket`).
- **Суть:** `getOrderStatus`→`client.fetchOrder` возвращает `OpenOrder` и отдаёт
  `null` при любой ошибке И, вероятно, для уже исполненного/истёкшего ордера
  (он больше не «open»). Тогда ветка `else` → `status='unfilled'`, шаг НЕ идёт
  в `pending_resolve`, `RedeemService` его не заклеймит, прогрессия теряет шаг —
  при том что акции реально куплены.
- **Фикс:** при `null`/не-open статусе не считать «unfilled» вслепую. Варианты:
  сверяться через сделки/позиции (`listAccountTrades`/`listPositions` из
  `@polymarket/client`), либо писать `pending_resolve` и дать резолверу
  разобраться по факту исхода. Сначала ПРОВЕРИТЬ поведение `fetchOrder` на
  исполненном GTD (ручной тест), чтобы выбрать точный фикс.

### 3. Осиротевший resting-ордер после рестарта
- **Где:** `src/trading/trading.service.ts:442` (`onModuleInit` — восстановление).
- **Суть:** `restingOrder`/`positioned` живут только в памяти. На старте
  восстанавливается лишь `pendingByStream` из БД; открытые ордера на бирже НЕ
  сверяются, `cancelAll` не зовётся. Рестарт во время открытого окна с висящей
  GTD-лимиткой → ордер живёт, может исполниться, а бот о нём забыл.
- **Фикс:** на старте в лайве сверить/снять открытые ордера (`client.cancelAll()`
  или сверка `listOpenOrders` с БД). Осторожно с несколькими потоками на одном
  аккаунте — снимать только релевантные токены.

## 🟡 Средний риск (корректность PnL/прогрессии)

### 4. Void / 50-50 маркет засчитывается как проигрыш
- **Где:** `src/polymarket/gamma-market.service.ts:163` + `trading.service.ts:1748`.
- **Суть:** `yesWon = yesPrice === 1`. При возврате/ничьей (`[0.5,0.5]`) оба
  `false` → `won=false` → попытка «слита», стейк сброшен, хотя деньги вернулись.
- **Фикс:** распознавать void (ни одна сторона ≠ 1) как push (не loss): шаг не
  засчитывать ни в win, ни в loss, стейк не сбрасывать; отдельный статус лога.

### 5. Гейт по балансу «fail-open» в лайве
- **Где:** `src/trading/trading.service.ts:954`.
- **Суть:** если `getUsdBalance()` вернул `null` (API баланса лёг), окно
  открывается БЕЗ гейта. Устойчивый сбой → торговля сверх средств.
- **Фикс:** в лайве fail-closed (пропустить окно) либо лимит на число подряд
  идущих fail-open открытий.

## 🟢 Низкий / полировка

### 6. Несогласованный дефолт `enabled` на экране настроек
- **Где:** `src/trading/trading.service.ts:585` (`?? true`) vs `:474` (`?? false`).
- **Суть:** ненастроенный поток показывается «включён», хотя реально на паузе.
  Только отображение. Фикс: привести `getCloseModes` к `?? false`.

### 7. Хрупкое сравнение исхода по float
- **Где:** `src/polymarket/gamma-market.service.ts:163`.
- **Суть:** `yesPrice === 1` — хрупко к формату оракула. Фикс: порог `>= 0.99`
  (совместно с п.4/void).

### 8. FAK «no orders to match» логируется как ERROR
- **Где:** ветка ошибки маркет-пути (лог 21:38:36–38, каждые ~800мс).
- **Суть:** ожидаемое состояние (нет предложений) шумит как ERROR, пока не
  подхватит лимитка. Фикс: распознавать эту конкретную ошибку и писать debug.

### 9. WS не чистит стакан при реконнекте до первого снапшота
- **Где:** `src/polymarket/market-ws-stream.ts` (`connect`/`scheduleReconnect`).
- **Суть:** краткое окно на устаревшей книге может накормить решение о входе.
  Низкий (гейты + позднее окно входа). Фикс: чистить `asks/bids` при реконнекте.

### 10. (смежное, из прошлого разговора) — снятие resting при потере фаворита
- **Где:** `src/trading/trading.service.ts` ранние `return` в decision-loop
  (`!favorite`, `bestBid < favoriteBidThreshold`).
- **Суть:** та же природа, что и уже закрытый блок тира: если сторона перестала
  быть фаворитом, но buy-лимитка на неё висит — держать нельзя.
- **Фикс:** снимать resting и в этих ветках (по логике «снимать всегда»).
