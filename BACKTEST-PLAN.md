# План: модуль бэктеста (Часть 2 — отложено на новую сессию)

Часть 1 (параллельное хранение тиков) уже реализована в Сессии 15 — см. `CHANGES-session-15.md`. Этот файл фиксирует план Части 2, чтобы не терять контекст между сессиями.

## Зачем откладываем

Часть 1 — низкая/средняя сложность, сделана за один заход. Часть 2 — полноценный отдельный подпроект, требующий аккуратности именно там, где дороже всего ошибиться (если бэктест хоть немного разойдётся семантикой с live-путём, он будет врать в самый ответственный момент — при принятии решения "включать фильтр или нет").

## Требование пользователя (дословно, важно сохранить)

> Бэктест должен быть по такой же логике, как и сейчас вот реальный on-time флоу, то есть прям смотрит по тикам свечи, смотрит по тикам полимаркет и ищет точки входа.

То есть НЕ отдельная "модель", реализующая ту же идею заново, а **честный повтор** существующего кода `evaluateEntryGate`/`computeTier`/`onBookUpdate` над историческими данными — иначе результат бэктеста и результат live легко разойдутся по причинам, не имеющим отношения к самим фильтрам.

## Компоненты

### 2.1 Абстракция источника данных (самое рискованное место)

Сейчас `PriceFeedService` и `MarketWsStream` жёстко привязаны к живым WS. Нужно:
- Выделить интерфейс (`IPriceSource`, `IBookSource` или похожий), под который подставляется либо живая реализация (как сейчас), либо `ReplayPriceSource`/`ReplayBookSource`, читающие `price_ticks`/`polymarket_price_ticks` по историческим ts.
- Replay-реализация должна воспроизводить ТУ ЖЕ последовательность событий и с той же семантикой (`applyTrade`, обновления книги), что и живой источник — иначе то, что бэктест "увидел бы" в момент X, не будет совпадать с тем, что видел бы live-бот.
- Риск: если тиков в истории меньше, чем было бы в реальности (recorder мог на секунду отвалиться) — бэктест должен честно показывать "данных недостаточно" на этом отрезке, а не тихо интерполировать (та же fail-closed философия, что и везде в проекте).

### 2.2 Виртуальные часы

Вся логика, использующая `Date.now()` (`timeLeftSec`, таймауты лимиток, `evaluateEntryGate`, `computeTier`), должна параметризоваться "текущим временем бэктеста". Практически — завести обёртку `IClock` (`now(): number`), либо явно прокидывать `nowMs` во все точки, где сейчас `Date.now()` (потребует ревизии `trading.service.ts`, `price-feed.service.ts`).

### 2.3 Симуляция исполнения без реальной биржи

- Правило A (маркет-тейк) — можно честно симулировать по историческому снимку книги Polymarket (`polymarket_price_ticks` уже хранит bid/ask, можно переиспользовать `book-fill.util.ts` для расчёта VWAP-заполнения).
- Правило B (лимитка-фолбэк) — сложнее: в реальности исполнение подтверждается через WS-событие "наш ордер исполнился" (мы часть книги). В бэктесте нужно эмулировать: если в исторической книге на нашем тире появлялся встречный объём по нашей цене/ниже — считаем исполненным. Здесь тоже переиспользуется `book-fill.util.ts`, но нужно аккуратно решить, что считать "нашим ордером, стоящим в книге" (влияет ли наш гипотетический ордер на глубину для следующего снимка — скорее всего нет, историю не переписываем, но это упрощение нужно явно задокументировать как ограничение бэктеста).

### 2.4 API + UI

- `POST /backtest/run` (новый контроллер, по образцу `AnalyticsController`) с параметрами:
  - диапазон дат, `streamKey`(-и),
  - набор ENV-оверрайдов (все текущие + будущие ENV гейта/фильтров/окон — `ENTRY_FILTER_ENABLED`, `MIN_DISTANCE_ATR_RATIO`, все 4 фильтра Сессии 13, `LAST_ENTRY_WINDOW_SEC`/`LIMIT_TIER2/3_SECONDS` и их per-stream варианты Сессии 14).
- Ответ — сводка в духе таблицы, которую пользователь присылал вручную (входы/анфиллед/скип/прибыль, средняя цена входа и т.д.), возможно с постраничным списком отдельных смоделированных сделок для разбора.
- UI — минимальная HTML-страница поверх уже существующей статики (`IS_STATIC`/`public/`, CORS уже включён в `main.ts`), с формой параметров и кнопкой "запустить" — не полноценный фронтенд-проект, а рабочий инструмент.

### 2.5 Оценка объёма

Не однодневная задача — реалистично несколько сессий:
1. Абстракция источника данных + виртуальные часы (2.1-2.2) — ядро, без него остального смысла нет.
2. Симуляция исполнения (2.3).
3. API + UI (2.4) — можно делать параллельно/после, это самая механическая часть.

## Зависимости от Части 1

Бэктест не может стартовать раньше, чем накопится реальная история в `price_ticks`/`polymarket_price_ticks` (см. Сессию 15) — реалистично нужно минимум несколько дней данных, покрывающих оба потока (5m/15m) и желательно хотя бы один реальный убыток, чтобы было на чём проверять поведение при проигрыше.

## Что НЕ делать

- Не пытаться "предсказать" правильные пороги фильтров через ML/статистику по малой выборке — сначала нужен рабочий честный replay существующей логики, потом уже эксперименты с порогами поверх него.
- Не переписывать `evaluateEntryGate`/`computeTier` под бэктест "по мотивам" — именно переиспользование, не копия с дрейфом логики.
