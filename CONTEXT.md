# polymarket-smoke — контекст проекта

## Что это

Бот для Polymarket-маркетов "Up or Down" (BTC/SOL/ETH/... по 5m/15m/1h),
реализующий стратегию реинвест-прогрессии "N шагов подряд без единого сбоя"
(challenge на N побед подряд, при проигрыше — сброс на базовый стейк).
Цель — набрать почти-гарантированный исход (¢99+) по одному из двух
бинарных outcome (YES/NO), реинвестируя выигрыш в следующий шаг.


Стек: TypeScript / NestJS, TypeORM + PostgreSQL, WebSocket (Polymarket CLOB
market-стрим + внешний ценовой фид), React-дашборд без сборки
(`index.html`, babel standalone в браузере).

Изначально был написан для одного актива/таймфрейма с общим счётчиком
шагов; в ходе этой серии сессий переведён на архитектуру с несколькими
независимыми потоками (актив × таймфрейм), каждый со своей прогрессией.

## Архитектура (ключевые файлы)

- `src/trading/trading.service.ts` — ядро: обнаружение маркетов, два правила
  входа (маркет-тейк / лимитка-фолбэк), запись логов, резолвер, реинвест-
  прогрессия. Самый большой и самый важный файл.
- `src/trading/stream-config.ts` — `STREAMS_CONFIG` (JSON из .env): список
  независимых потоков (`streamKey`, таймфрейм, формат слага, базовый стейк).
- `src/polymarket/gamma-market.service.ts` — читает Gamma API Polymarket
  (публичный, без ключа): текущий/следующий маркет по слагу, исход после
  резолва. Параметризован по `StreamDefinition` — умеет строить слаги двух
  разных форматов (unix-based для 5m/15m, календарный ET-based для 1h).
- `src/polymarket/price-feed.service.ts` — внешний ценовой фид для
  диагностики/ATR-гейта (НЕ тот же путь, которым сам Polymarket резолвит
  маркет через свой CLOB, но с недавних изменений — тот же ИСТОЧНИК цены,
  см. ниже). Мульти-провайдерный, с авто-фолбэком и ATR, масштабируемым под
  таймфрейм каждого потока.
- `src/polymarket/clob-public.service.ts` — публичный CLOB API (лучшая
  котировка, полный стакан, тик-сайз, минимальный размер ордера).
- `src/polymarket/market-ws-stream.ts` — WS-подписка на живой стакан
  конкретного маркета (book/price_change/tick_size_change).
- `src/polymarket/book-fill.util.ts` — честный проход по уровням стакана
  (VWAP), а не "весь объём по лучшей цене".
- `src/polymarket/polymarket-trader.service.ts` — боевой торговый клиент
  (`@polymarket/clob-client`), используется только при `SMOKE_START=false`.
- `src/entities/attempt.entity.ts`, `market-log.entity.ts` — состояние
  попытки (шаг, стейк) и лог каждого шага (диагностика, исход, профит).
- `src/analytics/analytics.controller.ts` — `/analytics/summary`,
  `/analytics/losses`: бэнкролл, разбивка по потокам, лучшие попытки.
- `index.html` — дашборд: табы по бэкендам (разные деплои под разные
  активы) + табы по потокам (таймфреймы внутри одного бэкенда).
- `scripts/verify-trading-logic.ts` — ad-hoc юнит-тесты на фейках (без БД и
  сети), гоняется через `npx tsx`. **Держать в актуальном состоянии** —
  единственная защита от регрессий при следующих правках.
- `scripts/measure-book-depth.ts` — отдельный долгоживущий процесс, копит
  JSONL со реальной ask-глубиной на ¢99+ по каждому потоку (для проверки,
  реалистична ли цель "N шагов подряд" с точки зрения ликвидности).
- `BACKLOG.md` — план на будущее (пункты 5-7 ещё не реализованы: генерализация
  GammaMarketService под 4ч/1д, приоритизация таймфреймов, Above-маркеты как
  отдельный трек, политика капитала по потокам).

## Что уже сделано (хронологически, по сессиям)

### Сессия 1 — независимые потоки + реинвест-прогрессия (BACKLOG п.1-4)
- Раньше был ОДИН общий счётчик шагов на все активы сразу и константная
  ставка (`BET_AMOUNT`). Теперь `STREAMS_CONFIG` — независимые потоки
  (`streamKey` = актив×таймфрейм), у каждого свой `Attempt`, свой прогресс.
- **Реинвест-прогрессия**: `Attempt.currentStake` не константа. Старт
  попытки = `baseStake` потока; после каждого выигрыша
  `currentStake = filledAmount/entryPrice` — по ФАКТИЧЕСКОЙ цене исполнения
  этого шага (VWAP гуляет по тирам лимитки/маркет-тейка), не по константе
  ¢99. При проигрыше — новая попытка, сброс на `baseStake`.
- Слаги маркетов проверены вручную на живых данных: 5m/15m —
  `{prefix}-{unix_start}`; 1h — календарная ET-строка
  (`bitcoin-up-or-down-september-9-2026-7pm-et`), НЕ unix-таймстамп.
  `GammaMarketService` умеет оба формата через `kind: 'interval'|'hourly-et'`.
- `scripts/measure-book-depth.ts` добавлен для замера реальной глубины
  стакана перед тем, как доверять цели "500 шагов" как достижимой.
- Фронтенд: карточки прогресса и таблица попыток теперь показывают
  `streamKey` и текущий стейк, а не общий счётчик.

### Сессия 2 — фикс WS Binance (гео-блок) + мульти-провайдерный фид
- Реальный инцидент: Binance WS отвечал `451 Unavailable For Legal Reasons`
  на handshake (гео-блокировка по IP хостинга) — фид был мёртв ВСЮ сессию,
  а не эпизодически, вся диагностика (`referencePrice`/`priceAtEntry`)
  отсутствовала на 100% входов.
- Исправлено: `PriceFeedService` теперь мульти-провайдерный
  (`FEED_PROVIDERS`), с авто-переключением после N подряд неудачных
  подключений (`FEED_PROVIDER_FAIL_THRESHOLD`). Плюс опциональный прокси
  (`FEED_PROXY_URL`, http/https/socks5) на случай, если геоблок задевает
  все провайдеры сразу.

### Сессия 3 — окно входа + ATR-гейт fail-closed (по реальным сливам)
- Разобраны два реальных слива на eth-updown-5m: оба случились на РАННИХ
  входах (ask по ¢99 появлялся за 2-3 минуты до закрытия, рынок ещё не
  "определился", цена успевала развернуться).
- Добавлено: `LAST_ENTRY_WINDOW_SEC` (по умолчанию 60) — ни Правило A, ни
  Правило B вообще не пытаются войти раньше последней минуты до закрытия.
  Тиры лимиток (`LIMIT_TIER2/3_SECONDS`) пересчитаны так, чтобы попадать
  внутрь этого окна (40с/15с вместо 150с/60с).
- `ENTRY_FILTER_ENABLED` теперь `true` по умолчанию (раньше был SHADOW-режим
  "считаем, но не блокируем"). Изменена логика при отсутствии диагностики:
  раньше fail-open (пропускали проверку, входили вслепую), теперь
  **fail-closed** — если фид не отдал ни одного тика к моменту входа, шаг
  ПРОПУСКАЕТСЯ целиком. Философия: упустить сделку лучше, чем потерять
  капитал вслепую.

### Сессия 4 — фронтенд: табы по потокам
- Добавлены клиентские (без доп. запросов) табы по `streamKey` (5m/15m/1h)
  внутри уже выбранного бэкенда/актива — независимо от старых табов
  BTC/SOL/ETH (которые остаются табами по РАЗНЫМ бэкенд-деплоям).
- При выборе конкретного потока показывается его собственная сводка
  (wins/losses/profit), при этом общий бэнкролл остаётся глобальным
  (намеренно — один кошелёк на все потоки сразу).

### Сессия 5 — самый важный разбор: источник цены и масштаб ATR (по логам реальных сливов BTC/SOL)
- **Найден и заменён источник эталонной цены.** Раньше референс/ATR
  считались по Binance/Bybit — приближение, НЕ то, чем Polymarket реально
  резолвит крипто Up/Down маркеты (Chainlink, data.chain.link). Это и
  объясняло расхождения (напр. Bybit-свеча open/close заметно отличались от
  официального "Price to Beat" на самом Polymarket).
  Найден официальный бесплатный источник — Polymarket сам транслирует
  Chainlink-цену через публичный WS `wss://ws-live-data.polymarket.com`
  (топик `crypto_prices_chainlink`, без API-ключа, задокументировано на
  docs.polymarket.com). Теперь это провайдер **по умолчанию**
  (`FEED_PROVIDERS=chainlink,binance,bybit`), Binance/Bybit — фолбэк.
  В каждый `market_logs` пишется `priceSource` — видно, откуда именно
  диагностика в конкретной сделке.
- **Найден реальный баг в расчёте ATR (в два захода).** Раньше ATR считался
  по свечам в 1 секунду × 20 штук = 20-секундное окно, ОДИНАКОВОЕ для
  5-минутного и часового маркета — давало обманчиво ОГРОМНЫЙ
  `atrRatioAtEntry` (45-60x) при почти равновероятных входах, потому что
  типичный шум за 20 секунд на порядки меньше типичного дрейфа цены за
  15-60 минут.
  Первая правка (свеча = `intervalSec/FEED_ATR_CANDLES`, т.е. окно делилось
  на 20 кусков) была ШАГОМ В ПРАВИЛЬНУЮ СТОРОНУ, но всё ещё математически
  неверной: сравнивать дрейф цены за ВСЁ окно с размахом ВНУТРИ 1/20 этого
  окна некорректно, поскольку при случайном блуждании размах растёт
  примерно как √(время) — то есть даже на чистом шуме без всякого
  направленного движения такое сравнение само по себе давало бы
  коэффициент ≈√20≈4.5, а не ≈1.
  Финальное исправление: одна свеча ATR = РОВНО ОДНО ЗАВЕРШЁННОЕ ОКНО
  потока (`intervalSec`), ATR = средний размах последних N таких окон —
  прямое сравнение "насколько обычно двигается цена за один такой же по
  длине маркет", без пересчётных коэффициентов. Плата — более долгий
  прогрев (`N*intervalSec`): 100 минут для 5m, 5 часов для 15m; у часового
  потока `atrCandles` в `STREAMS_CONFIG` уменьшен до 8 (иначе было бы 20
  часов). Пока прогрев не набрался — `atr` возвращает `null`, что при
  `ENTRY_FILTER_ENABLED=true` уходит в fail-closed так же, как отсутствие
  тиков. `StreamDefinition` теперь поддерживает необязательное поле
  `atrCandles` для переопределения числа свечей на конкретный поток.
  Проверено тестом: несколько потоков, шарящих один тикер (напр. все
  BTC-потоки), ведут независимые свечные серии с разным размером свечи и
  разным числом свечей в ATR.
- Добавлена проверка "протухшего" тика (`FEED_STALE_MS`, по умолчанию 5с) —
  если последний тик по фиду старше порога, диагностика считается
  недоступной (не берётся "какая есть"), что при включённом гейте уходит в
  fail-closed так же, как полное отсутствие тиков.
- Добавлены колонки `orderSentAt`/`orderFilledAt` в `market_logs` — момент
  отправки/выставления ордера и момент фактического исполнения, отдельно от
  цены на входе (нужно для разбора инцидентов "цена успела уйти между
  решением и фактом").
- Прояснено (без изменения кода): реинвест-прогрессия считает от
  `filledAmount/entryPrice`, не от теоретической "чистой" ставки — если по
  пути были частичные исполнения (`fillRatio < 1`), рост будет медленнее
  идеальной геометрии. Это не баг, а следствие честного реинвеста только
  реально вложенных денег.

## Известные открытые вопросы / не сделано

- BACKLOG.md п.5-7 не реализованы: генерализация под 4ч/1д, Above-маркеты
  как отдельный трек, единая политика капитала между потоками.
- `BLOCK_ORDERS_IF_PENDING` упоминается в `.env.example`/BACKLOG.md как
  "уже сделано", но физически не реализован в коде — это несостыковка,
  оставшаяся от исходного проекта до начала этой серии сессий, ещё не
  исправлена.
- `MIN_DISTANCE_ATR_RATIO` (порог ATR-гейта, по умолчанию 1.5x) не
  откалиброван на новой (окончательно исправленной) шкале ATR — стоит
  пересчитать по накопленной статистике после того, как отработает какое-то
  время с Chainlink-фидом и правильным масштабом свечей (окно = целое
  прошлое окно потока, не его доля).
- **Операционный нюанс новой схемы ATR**: пока не набрался прогрев
  (`atrCandles * intervalSec` — 100 мин для 5m, 5ч для 15m, 8ч для 1h),
  `atr` = `null`, и при `ENTRY_FILTER_ENABLED=true` (дефолт) это означает
  вообще НИ ОДНОЙ сделки на свежезапущенном потоке, пока прогрев не
  наберётся. Это ожидаемо (fail-closed по дизайну), но стоит иметь в виду
  при перезапуске бота или добавлении нового потока — прогресса по шагам не
  будет до истечения прогрева.
- Явного "гейта на расхождение источников" (напр. "если bybit и chainlink
  показывают разное направление — пропустить") не добавлено — решили, что
  переход на Chainlink как основной источник закрывает эту проблему по
  построению; расхождение фолбэк-провайдеров с реальностью видно постфактум
  через `priceSource` в логах, но не блокируется на лету.
- Фронтенд (`index.html`) собран без сборщика (JSX через babel-standalone в
  браузере) — при правках стоит прогонять через `@babel/standalone` в node
  для быстрой проверки синтаксиса перед выкаткой (без браузера).

## Порядок работы над задачами (фиксированный процесс)

При любой следующей серии правок — придерживаться этой последовательности,
именно в таком порядке. Смысл фиксации здесь: этот же порядок и этот же
формат плана можно перенести в новый чат (даже без остального контекста
сессии) и повторить один в один.

1. **Разбор.** Прочитать код (не гадать по названиям файлов), найти
   реальную причину/место каждого пункта задачи. Для багов — дойти до
   конкретной строки/механизма, а не до симптома.
2. **План.** Сформулировать план настолько явно, чтобы его можно было
   выполнить в новом чате по одному этому описанию: список конкретных
   файлов, что именно меняется в каждом (новая сущность/поле/эндпоинт/метод),
   в каком порядке, и какие инварианты это должно сохранить/восстановить.
   План публикуется целиком ДО начала правок.
3. **Исполнение.** Выполнить план целиком за один проход (не по одному пункту
   с ожиданием подтверждения) — бэкенд, фронтенд, миграции/схема, `.env.example`.
4. **Сдача.** Полный архив проекта (не патчи/диффы) + отдельно `.env.example`
   + краткое резюме, что изменилось и что нужно сделать руками (переменные
   окружения, разовые миграции).

## Сессия 6 — план (в работе)

Разбор (см. код) и план по семи пунктам, зафиксированным пользователем:

1. **Отдельная ручка списка ставок (не грузить `/analytics/summary`).**
   Новый `GET /analytics/trades?limit=&streamKey=&status=` в
   `analytics.controller.ts` — плоский список последних N `MarketLog` по ВСЕМ
   потокам сразу (активные `pending_resolve` и исторические), с
   `eventUrl` (см. п.2) и `attemptNumber`/`attemptId` через джойн на `Attempt`.
   Без тяжёлых агрегатов — просто выборка + пагинация. `/analytics/summary`
   не трогаем.
2. **Ссылка на событие у активной ставки.** `eventUrl` = `https://polymarket.com/event/{slug}`,
   считается на бэкенде (маленький хелпер) и отдаётся в `/analytics/trades`,
   `/analytics/streams/:streamKey`, `/analytics/attempts/:id`.
3. **Переход на "событие" = поток (streamKey).** `GET /analytics/streams/:streamKey` —
   все `MarketLog` этого потока по ВСЕМ попыткам (история + активные), плюс
   краткая шапка (сколько попыток, суммарный профит потока). Понятие
   "событие" в терминах пользователя = повторяющийся ряд маркетов одного
   потока (напр. все окна btc-updown-5m), а не единичный слаг.
4. **Переход на конкретную попытку.** `GET /analytics/attempts/:id` — один
   `Attempt` + все его `MarketLog` (шаги), т.е. именно то, что просил
   пользователь: результаты/история/активные ставки/цена входа одной попытки.
5. **Досрочное закрытие попытки.** `AttemptStatus` + `'closed_early'`.
   `POST /trading/attempts/:id/close-early` (новый `trading.controller.ts` в
   `TradingModule`, метод `TradingService.closeAttemptEarly`): помечает
   попытку `closed_early`+`finishedAt`, сразу создаёт для того же `streamKey`
   новую активную попытку со сбросом на `baseStake` (как при проигрыше) —
   бот продолжает торговать потоком без ручного рестарта. Если по потоку
   есть незарезолвленный шаг — он доедет своим резолвом (профит запишется
   в лог), но уже не повлияет на прогрессию закрытой попытки.
6. **Кеш истории свечей для ATR (вместо ожидания прогрева часами).**
   Архитектура: PostgreSQL как постоянное хранилище (не Redis — она у нас уже
   есть, транзакционна, не нужен ещё один сервис), REST-бэкафилл при
   старте, WS — единственный источник вперёд по времени.
   - Новая сущность `PriceCandle` (`ticker`, `intervalMs`, `startMs`, OHLC,
     уникальный индекс `ticker+intervalMs+startMs`).
   - Новый `CandleHistoryService` (`src/polymarket/candle-history.service.ts`):
     `bootstrap(ticker, intervalMs, need)` — сперва читает последние `need`
     свечей из БД; если не хватает, догружает недостающее через публичный
     Binance REST `GET /api/v3/klines` (интервалы 5m/15m/1h у Binance
     совпадают с нашими потоками один в один) и апсертит в БД. Дальше
     `saveClosedCandle(...)` вызывается из `PriceFeedService` при закрытии
     каждой живой свечи — БД всегда содержит "хвост" истории для мгновенного
     рестарта без нового многочасового прогрева.
   - `PriceFeedService.onModuleInit` теперь `async`: для каждого потока
     сначала `bootstrap(...)`, кладёт результат в `state.closed`, и только
     потом коннектится по WS.
7. **Race condition по сумме ставки (реальный баг, найден).** Причина: в
   `discoveryTick` новое окно потока открывается сразу по смене unix-бакета,
   НЕЗАВИСИМО от того, зарезолвился ли Gamma-резолвером предыдущий шаг этого
   же потока. `betAmount` нового окна снимается с `Attempt.currentStake` в
   момент открытия — если предыдущий шаг ещё `pending_resolve` (Gamma может
   отвечать `closed:true` с задержкой, больше интервала окна), следующее
   окно открывается с ТЕМ ЖЕ (не выросшим и не сброшенным) стейком — отсюда
   и "несколько шагов подряд по одной и той же сумме" в логах пользователя.
   В .env.example уже был описан (но не реализован) `BLOCK_ORDERS_IF_PENDING` —
   реализуем именно его:
   - `TradingService.pendingByStream: Map<streamKey, Set<marketLogId>>`,
     заполняется при записи лога со статусом `pending_resolve`, чистится в
     `resolvePendingMarkets` по мере резолва; восстанавливается из БД в
     `onModuleInit` (на случай рестарта процесса).
   - `discoveryTick` пропускает поток целиком (не идёт даже за маркетом на
     Gamma), пока `pendingByStream.get(streamKey)` не пуст и
     `BLOCK_ORDERS_IF_PENDING=true`.
   - Побочная правка: `MarketState` теперь хранит собственный снимок
     `attemptId`/`attemptStepNumber` (сделанный в момент открытия окна), и
     `writeLog` использует именно его, а не `currentAttempts.get(streamKey)`
     в момент записи — раньше между открытием окна и записью лога
     (десятки секунд) `currentAttempts` для потока мог успеть смениться
     (например из-за досрочного закрытия, см. п.5), и лог/шаг ушёл бы не в
     ту попытку.
   - Предложенный пользователем альтернативный подход ("предрезолв" по
     сравнению open N-1 со close N-2 через историю Chainlink) в этой сессии
     сознательно НЕ был реализован (аргумент см. в git-истории/предыдущей
     версии этого файла) — **ПЕРЕСМОТРЕНО в Сессии 7 ниже**, реализован как
     отдельный опциональный режим, а не замена блокировке.

   Также применён фикс пользователя в `PriceFeedService`: первый фрейм
   Chainlink RTDS иногда приходит пустой строкой — до `JSON.parse` добавлена
   проверка `message.trim()`.

## Сессия 8 — 4 бага из прод-логов (компаундинг, спам, ATR, Bybit-ревью)

**1. Компаундинг "проваливался" почти до базового стейка при частичном филле.**
Найдено в `resolvePendingMarkets`/`tryPreResolve`: `attempt.currentStake` при
выигрыше считался ТОЛЬКО как `spentUsd/entryPrice` (`spentUsd` = реально
исполненная сумма, `filledAmount`). Если ордер исполнялся частично (заявка
$6.36, реально куплено $4.95 из-за нехватки глубины стакана на маркет-тейке —
ровно случай из прод-лога пользователя), неисполненный остаток ($1.41)
просто нигде не учитывался: он не проигран, не поставлен — но и не попадал
в следующий стейк. Прогрессия визуально "откатывалась" почти к baseStake
при каждом частичном филле, хотя формально это была серия побед. Фикс: к
`spentUsd/entryPrice` прибавляется `max(0, betAmount - spentUsd)` —
неисполненные деньги возвращаются в оборот вместо того, чтобы молча выпадать
из прогрессии. Применено синхронно в обоих местах, где считается тот же
стейк выигрыша: `resolvePendingMarkets` (официальный резолв) и
`tryPreResolve` (предсказание, Сессия 7).

**2. Спам в логах.** `discoveryTick` крутится каждые `MARKET_DISCOVERY_POLL_MS`
(1.5с по умолчанию) — при `PENDING_GATE_MODE=block`/неуверенном
`pre_resolve` каждый тик писал одинаковую DEBUG-строку "пропуск нового
окна...", то же самое было с `[STALE]`-предупреждением на 10-секундном
пуле резолва. Добавлен троттлинг (`lastGateSkipLogAt`, ключ на поток или
`stale:<logId>`): пропуски окна — не чаще раза в 30с
(`GATE_SKIP_LOG_THROTTLE_MS`), `[STALE]` — не чаще раза в
`STALE_RESOLVE_WARN_MS`. Троттлинг сбрасывается сразу, как только шаг
резолвится — следующий реальный эпизод залогируется без задержки.

**3. Периодическая "недоступность свечей" для ATR-гейта.** Причина —
та же геоблокировка Binance с американского IP, что и в п.4: если бэкафилл
(`CandleHistoryService.bootstrap`) не находил свечей ни в БД, ни через
Binance REST, `PriceFeedService.onModuleInit` **не логировал вообще ничего**
в случае нулевого результата (логировались только "полный прогрев" и
"частичный прогрев", ветка "0 свечей" была пустой) — из-за этого ATR-гейт
молча уходил в fail-closed (`evaluateEntryGate`, п. `atrRatioAtEntry == null`)
без единой диагностической строки о причине. Внешне выглядело как случайные
пропуски входа "через раз" (особенно заметно сразу после рестартов —
частых на этапе тестирования). Исправлено двумя способами: (а) добавлен явный
`WARN` на нулевой результат бэкафилла с указанием, сколько свечей потребуется
накопить живому фиду; (б) добавлен Bybit REST как второй источник бэкафилла
(см. п.4) — сама причина нулевого результата устранена для сценария
"Binance недоступен из региона хостинга".

**4. Ревью правки пользователя: Bybit REST как фолбэк бэкафилла + перенос
сервера в Нидерланды.** Пользователь переписал `CandleHistoryService`,
добавив Bybit REST как второй источник (после Binance) на случай гео-
блокировки. Код принят почти как есть, с точечными правками:
- Порядок источников (БД → Binance → Bybit) и идемпотентный upsert —
  корректны, дублирование при пересечении диапазонов не проблема
  (уникальный индекс `ticker+intervalMs+startMs` гасит повторы).
- Фильтр "строго закрытая свеча" через `candle.start + intervalMs <= now`
  (вместо отбрасывания последнего элемента ответа) — правильнее и надёжнее,
  оставлено как в правке пользователя.
- Сортировка Bybit-ответа явно через `.sort()` — верно подстраховались:
  Bybit V5 kline отдаёт список в порядке убывания времени (новые первыми),
  в отличие от Binance (по возрастанию); код сортирует сам, так что не
  зависит от того, в каком порядке фактически ответит API.
- **Правка**: `category=linear` (бессрочные фьючерсы) заменено на
  `category=spot` — ATR тут используется как приближение исторической
  волатильности спота (к которому ближе Chainlink-фид, которым Polymarket
  и резолвит), а не как торговая пара с открытой позицией; спот чуть
  консистентнее с остальным пайплайном (разница на практике небольшая, но
  раз это переписывалось заново — поправили заодно).
- **Упрощение**: убраны дублирующиеся `getIntervalMsFromBinance`/
  `getIntervalMsFromBybit` (обратное отображение "строка интервала ->
  миллисекунды") — `intervalMs` и так известен в момент вызова
  `fetchFromBinance`/`fetchFromBybit` (передаётся из `bootstrap`), незачем
  восстанавливать его из строки интервала второй раз тем же кодом, что и
  прямое отображение (лишняя точка потенциального рассинхрона таблиц).
- Отдельно стоит логика хостинга: сам факт необходимости Bybit-фолбэка —
  следствие того, что Binance отдаёт 451/геоблок на REST из США (не только
  API-специфично — это IP-уровневая блокировка Binance для американских
  адресов). Bybit тоже может иметь свои региональные ограничения — если
  когда-нибудь оба REST-источника окажутся недоступны одновременно, теперь
  это будет явно видно по WARN из п.3, а не молчаливым fail-closed.



Пользователь обоснованно указал: сейчас проект на смоук-тестах, и в отличие
от произвольного "предсказания будущего", здесь сравнивается цена Chainlink —
то есть буквально тот же источник, которым Polymarket/Gamma официально
резолвит крипто up/down-маркеты. Чистая блокировка (`block`) в периоды, когда
Gamma отвечает `closed:true` с задержкой чаще одного раза, ведёт к заметным
пропускам шагов. Решение: пре-резолв реализован, но НЕ вместо блокировки, а
как явно выбираемый третий режим — пользователь взвешивает риск/скорость сам.

**Три режима `PENDING_GATE_MODE`** (`TradingService`, см. `.env.example`):
- `block` (дефолт, без изменений) — как в Сессии 6.
- `pre_resolve` — `discoveryTick` при непустом `pendingByStream` вызывает
  `tryPreResolve(streamKey)`:
  1. Берёт САМЫЙ ПОСЛЕДНИЙ (по `createdAt`) ещё не зарезолвленный
     (`pending_resolve`) `MarketLog` этого потока — именно от него зависит
     сумма следующего шага прогрессии.
  2. Сверяет ТЕКУЩУЮ цену `PriceFeedService.getSnapshot(streamKey)` со
     `referencePrice` (страйком) этого лога — знак дельты даёт предсказанную
     сторону (`YES`/`NO`), совпадение с `chosenOutcome` лога = предсказан
     выигрыш.
  3. Доверяет предсказанию, ТОЛЬКО если дистанция от страйка ≥
     `PRE_RESOLVE_MIN_ATR_RATIO` (дефолт 2, строже входного
     `MIN_DISTANCE_ATR_RATIO`) значений ATR — иначе слишком близко к границе,
     возвращает `null`.
  4. Если `null` (фида нет / лог без диагностики / близко к границе) —
     `discoveryTick` на ЭТОМ тике ведёт себя как `block` (безопасный
     фолбэк), не открывает окно вслепую.
  5. Если предсказан выигрыш — стейк = `filledAmount/entryPrice` предыдущего
     шага (как при обычном выигрыше); если проигрыш — `baseStake` (сброс, как
     при обычном проигрыше). `Attempt.currentStep/currentStake` при этом НЕ
     трогаются — они по-прежнему обновляются только официальным резолвером
     (`resolvePendingMarkets`), пре-резолв влияет ТОЛЬКО на сумму, с которой
     открывается новое окно, пока официального ответа ещё нет.
  6. Опенное окно помечается `MarketState.stakePredicted=true` +
     `predictedFromLogId` → пишется в `MarketLog.stakePredicted`/
     `predictedFromLogId` (новые колонки) — видно в `/analytics/trades` и на
     фронте, что сумма этого шага не подтверждена официально на момент входа
     (важно на смоук-фазе для доверия механизму перед боевыми деньгами).
  - **Защита от накопления риска:** `provisionalChainByStream` считает,
    сколько окон подряд открыто через предсказание без хотя бы одного
    официального подтверждения между ними; при достижении
    `PRE_RESOLVE_MAX_CHAIN` (дефолт 1) pre_resolve временно откатывается к
    `block`, пока не придёт подтверждение — то есть длинная серия задержек
    Gamma не может привести к неограниченно длинной цепочке непроверенных
    ставок, максимум одна "вперёд" от последнего подтверждённого шага.
  - Почему это безопаснее, чем кажется на первый взгляд: даже если
    предсказание неверно, ПРОФИТ/СТАТУС самого нового шага всё равно считает
    официальный резолвер Gamma по его собственному реальному исходу — ошибка
    предсказания сказывается только на СУММЕ, поставленной на этот один шаг
    (ограниченный, разовый риск), а не на прогрессии/бухгалтерии попытки в
    целом (та же защита `attempt.status !== 'active'` из Сессии 6 не даёт
    "уехавшему" логу повторно создать/сдвинуть попытку).
- `open` — легаси без какой-либо защиты (это и есть исходный баг Сессии 6),
  оставлен только для явного осознанного выбора.

Обратная совместимость: старый `BLOCK_ORDERS_IF_PENDING` продолжает работать,
если `PENDING_GATE_MODE` не задан явно (`true`→`block`, `false`→`open`), с
предупреждением в логе перейти на новую переменную.



- Фронтенд (`public/index.html`): добавлена отдельная вкладка сделок,
  ссылка на событие в каждой активной/исторической строке, кнопка
  "Закрыть досрочно" на активной попытке, простой drill-down по потоку и по
  попытке (модалка поверх текущего дашборда, без роутера — проект
  сознательно без сборщика). Полноценная client-side маршрутизация
  (отдельные URL на поток/попытку) не сделана — сочтено избыточным для
  одностраничного дашборда без сборки; при необходимости можно добавить
  `location.hash`-роутинг отдельной задачей.
- Бэкафилл `CandleHistoryService` умеет только Binance klines (публичный,
  без ключа) — Bybit REST-бэкафилл не добавлен (Bybit и так фолбэк-провайдер
  живого фида, не критично для бутстрапа истории).

## Сессия 9 — зомби-соединение фида + остаточный спам entry-гейта

Пользователь указал: после Сессии 8 (Bybit-бэкафилл, WARN на 0 свечей) ATR
всё равно "недоступен" **часами**, хотя свечи для бэкафилла у Bybit есть —
то есть причина не в бэкафилле вообще. Разобрано заново:

**Настоящая причина.** У `PriceFeedService` ОДНО активное WS-соединение сразу
на ВСЕ потоки/тикеры (`buildUrl(tickers)` подписывает всё разом на одного
текущего провайдера). Реконнект и ротация провайдера (`handleDisconnect`)
завязаны ИСКЛЮЧИТЕЛЬНО на событии `'close'`/`'error'` сокета. Но у "зомби-
соединения" — когда сервер (в проде это чаще всего был именно Chainlink RTDS)
перестаёт слать данные на уровне приложения, а TCP-сокет при этом остаётся
технически открытым — НИ `'close'`, НИ `'error'` не срабатывают вообще.
Раньше это означало: реконнект/ротация на другого провайдера просто никогда
не запускались, и фид мог висеть мёртвым часами — именно то, что видно в
логах (`referencePrice=н/д`, "фид ещё не отдал ни одного тика" на протяжении
многих окон подряд для ОБОИХ потоков, разделяющих один тикер "btc" — что
подтверждает: дело не в конкретном потоке, а в самом соединении целиком).

**Фикс: вотчдог "последнего трейда".** `PriceFeedService.lastAnyTradeAt`
обновляется на каждый успешно распарсенный трейд (независимо от того, на
какой стрим он фан-аутится). Отдельный таймер (`dataWatchdogTimer`, проверка
каждые `FEED_DATA_WATCHDOG_MS/2`) сверяет `Date.now() - lastAnyTradeAt`; если
тишина превышает `FEED_DATA_WATCHDOG_MS` (дефолт 20с — заметно больше
`FEED_STALE_MS`=5с, который про "не доверяй старой цене", а не про "соединение
мертво") — вызывается `ws.terminate()` (жёстче `close()`, не ждёт хендшейка
от уже не отвечающей стороны). Дальше событие `'close'` от `terminate()`
подхватывается штатным `handleDisconnect` — ровно тем же путём, что и обычный
разрыв связи, включая счётчик `consecutiveFailuresOnProvider` и ротацию на
следующего провайдера после `FEED_PROVIDER_FAIL_THRESHOLD` таких эпизодов
подряд. `lastAnyTradeAt` и сам таймер вотчдога переинициализируются в
`connect()` — иначе тишина, накопленная ДО реконнекта, тут же убила бы
свежее соединение, не дав ему ни единого шанса прислать трейд.

Проверено отдельным скриптом `scripts/verify-price-feed.ts` (сервис не
покрывается `verify-trading-logic.ts`, т.к. это разные классы): свежий трейд
не триггерит разрыв, тишина дольше порога триггерит `terminate()`, свежий
трейд после долгой тишины сбрасывает счётчик, `stopped=true` глушит вотчдог
полностью (на выключении сервиса).

**Остаточный спам (вторая часть жалобы).** Троттлинг из Сессии 8 покрывал
только `discoveryTick` (гейт "пропуск нового окна"). В этом же логе спамил
СОВСЕМ ДРУГОЙ вызов — `evaluateEntryGate`, срабатывающий на каждый тик
ордербука ВНУТРИ окна входа (`onBookUpdate`/`tryMarketBuy`), т.е. многократно
в секунду, пока гейт держит блокировку "диагностика недоступна". Добавлено
поле `MarketState.lastEntryGateLogAt` (троттлинг НА ОКНО, не глобальный —
окно и так живёт не дольше нескольких минут, новое окно = новый объект =
чистый счётчик) + `logEntryGateBlockThrottled` (не чаще раза в
`ENTRY_GATE_LOG_THROTTLE_MS`=15с), применено к обеим точкам логирования
блокировки (маркет-тейк и лимитка).

## Сессия 10 — два микрокейса слива (SOL 15m и 5m)

Пользователь прислал два конкретных слива с точными диагностическими
строками из `/analytics/losses` и скриншотами Polymarket с графиком и
правилами резолва. Разбор каждого отдельно — они оказались РАЗНОЙ природы.

**Микрокейс №1 (15m, ATR-рацио на входе 0.44x — НАЙДЕН РЕАЛЬНЫЙ БАГ).**
0.44x намного ниже `MIN_DISTANCE_ATR_RATIO` — по идее гейт обязан был
ЗАБЛОКИРОВАТЬ такой вход, а не пропустить его. Причина: `evaluateEntryGate`
для резюм-лимитки (SMOKE) проверялся **только один раз — в момент
ВЫСТАВЛЕНИЯ** (`placeOrReplaceLimit`). Дальше лимитка просто "висит",
ожидая, пока в стакане накопится нужный объём продавцов — это может занять
секунды, а может и почти всё окно. Диагностика ДЛЯ ЛОГА бралась заново
в момент фактического исполнения (`captureDiagnostics`), но САМ ФАКТ
исполнения гейтом уже не проверялся повторно — из-за этого капитал реально
рисковался в момент, когда цена успела откатиться почти обратно к
референсу (0.44x на исполнении против, судя по всему, куда более уверенного
рацио на момент выставления) — ровно "поздний разворот" из диагностики
слива, только разворот случился МЕЖДУ выставлением и исполнением лимитки,
а не между входом и резолвом, как это выглядело по логу.

Фикс: `onBookUpdate` (ветка накопленного объёма продавцов, SMOKE) теперь
вызывает `evaluateEntryGate` ЗАНОВО непосредственно перед исполнением. Если
гейт к этому моменту уже не пропускает — лимитка отменяется
(`restingOrder=null`, `skippedLimitTier=tier`), сделка НЕ исполняется на
устаревшем разрешении. Если стрим ещё успеет дать новую уверенную цену до
закрытия окна — обычная логика входа (`onBookUpdate`/`placeOrReplaceLimit`)
переоценит гейт заново и сможет выставить новую лимитку с чистого листа.
Покрыто тестом 4b в `verify-trading-logic.ts` (гейт пропускает выставление
при рацио 5x, цена собеседуется, гейт блокирует исполнение при рацио 0.2x —
ожидаем отмену, а не слепое исполнение).

Отдельно отмечено: LIVE-режим (не SMOKE) пока не проверяет этот же
сценарий — там фактическое исполнение лимитки определяется через
`getOrderStatus` только в `finalizeMarket` (на закрытии окна), а не сразу по
факту филла. Поскольку сейчас проект целиком в SMOKE-фазе, это не
блокирует, но ДО перехода на LIVE-деньги нужно сделать симметричный фикс
там же (перепроверять гейт, как только придёт подтверждение реального филла
от биржи, а не постфактум на закрытии).

**Микрокейс №2 (5m, ATR-рацио на входе 1.74x) — ИЗНАЧАЛЬНОЕ объяснение
через TWAP было НЕПОЛНЫМ, см. пересмотр в Сессии 11 ниже.** На момент
разбора в этой сессии показалось, что гейт отработал корректно (наш
Chainlink-фид на закрытии показывал ту же сторону NO), а расхождение с
официальным резолвом Polymarket (`Up`) объяснялось методологией TWAP.
Пользователь на следующей итерации указал на официальный "Price To Beat"
с того же самого окна на скриншоте Polymarket ($102.03) — и наш
`referencePrice` для ЭТОГО ЖЕ окна был $102.128501466526, то есть отличался
от официального страйка почти на $0.10 — величина, СРАВНИМАЯ с самим ATR
(~$0.06). Это переворачивает объяснение: дело не (только) в TWAP-методологии
резолва, а в том, что наш референс для гейта уже был построен на неверном
страйке — см. настоящую причину и фикс в Сессии 11.

Важно: сам исход (win/loss) в системе и так берётся из ОФИЦИАЛЬНОГО ответа
Gamma API (`resolvePendingMarkets`/`fetchOutcome`), а не из нашего фида — то
есть бухгалтерия победы/поражения всегда верна независимо от этого
наблюдения. Проблема только в том, что ATR-гейт (решение "входить или нет" и
"с какой стороны") принимает решение по метрике, которая систематически НЕ
идентична тому, чем реально резолвится маркет — то есть некоторая часть
дисперсии/сливов объясняется этим методологическим зазором, а не шумом или
багом. Это НЕ исправлено в этой сессии (требует отдельного решения —
например, приближать TWAP через скользящее среднее по `state.closed`/тикам
за окно вместо точечной цены, либо явно принять этот зазор как источник
шума стратегии) — зафиксировано здесь как важное наблюдение для дальнейшей
работы, а не как баг с готовым фиксом.

## Сессия 11 — найдена настоящая причина смещённого referencePrice

Пользователь пересчитал таймстемп окна из микрокейса №2 (Сессия 10) вручную:
`sol-updown-5m-1789232400` = ровно 12 сентября, 13:00-13:05 ET — ТО САМОЕ
окно со скриншота, где официальный Polymarket "Price To Beat" = $102.03.
Наш `referencePrice` для этого же окна был $102.128501466526 — расхождение
почти $0.10, намного больше типичного ATR ($0.06) для этого потока. Это
не микро-шум, а систематическая ошибка — переоткрыл разбор реакции гейта:
причина не в TWAP-методологии (Сессия 10), а в том, ЧТО именно и КОГДА мы
берём за референс окна.

**Найденная причина.** `openMarket` брал `referencePrice` через
`priceFeed.getSnapshot(streamKey)` — то есть "текущую" (самую свежую)
цену фида НА МОМЕНТ ВЫЗОВА этой строки. Но до этой строки внутри того же
`openMarket` (и до него — в `discoveryTick`) уже произошло 1-3 сетевых
round-trip'а: `gamma.fetchMarketBySlug` (REST к Gamma) и
`Promise.all([clobPublic.getBestQuote(yes), clobPublic.getBestQuote(no)])`
(REST к CLOB) — только ПОСЛЕ них шёл захват референса. То есть наш референс
систематически (не случайно!) отставал по времени от истинного момента
официального старта окна на секунды — за эти секунды цена SOL вполне
успевает отойти на величину, сравнимую с самим ATR, из-за чего вся
дальнейшая ATR-гейт-математика (дельта/рацио/сторона) считалась от
СМЕЩЁННОГО якоря. Это объясняет оба микрокейса Сессии 10 разом лучше, чем
TWAP-гипотеза: смещённый референс сам по себе может давать неверную сторону
входа или заниженную/завышенную уверенность, независимо от того, как именно
резолвится сам маркет.

**Фикс — точечный поиск цены по буферу сырых тиков.** Раньше единственным
хранилищем цены был `state.lastPrice` (последний тик, без истории) и
`state.closed`/`state.current` (агрегаты-свечи для ATR, разрешением в целую
свечу — тоже недостаточно для "цена ровно в 13:00:00.000"). Добавлено:
- `StreamFeedState.recentTicks` — буфер сырых `{ts, price}` за последние
  `FEED_RECENT_TICKS_RETENTION_MS` (дефолт 15с — с запасом относительно
  `discoveryPollMs` + типичных REST round-trip'ов), пополняется в `applyTrade`,
  автоматически подрезается по возрасту на каждый новый тик.
- `PriceFeedService.getPriceAt(streamKey, targetMs)` — ищет в буфере
  последний тик с временем `<= targetMs` (т.е. "какая цена была ИЗВЕСТНА на
  тот момент", а не текущая); если буфер не достаёт так далеко назад
  (например только что переподключились) — честно возвращает `null`, а НЕ
  приближение текущей ценой (приближение и было исходным багом).
- `discoveryTick` теперь прокидывает `windowStartTs` (уже вычисленный
  `gamma.currentIntervalStartTimestampSec`) через `openMarket` в
  `getPriceAt(streamKey, windowStartTs * 1000)` вместо `getSnapshot()` —
  референс теперь ВСЕГДА цена на точный официальный момент старта окна, а
  не "текущая цена, когда мы туда добрались". `getSnapshot()` для
  `priceAtEntry`/`priceAtClose` (диагностика в момент реального решения о
  входе/на закрытии) оставлен без изменений — там как раз нужна именно
  "текущая" цена на момент принятия решения, это не референс/страйк.

Покрыто новыми тестами в `scripts/verify-price-feed.ts` (Тест E: точный
поиск по буферу, включая случай "цель старше всего буфера -> null, не
приближение"; Тест F: `applyTrade` пополняет и подрезает буфер по возрасту).

## Сессия 12 — симметричный фикс на закрытие + видимость лага в логах

Пользователь уточнил (правильный вопрос): "мы теперь точно корректно берём
цену старта окна?", попутно предложив свою схему хранения тиков и явно
попросил видеть цену открытия в логах. По факту оказалось: буфер сырых
тиков уже есть (Сессия 11), лог уже содержит `referencePrice` — но при
ревизии нашёлся симметричный недосмотр: **фикс Сессии 11 применили только к
ОТКРЫТИЮ окна, а ЗАКРЫТИЕ (`priceAtClose`/на закрытии в диагностике сливов)
всё ещё бралось через `getSnapshot()`** — "текущую" цену на момент, когда
фактически исполнился код `finalizeMarket`, а не цену РОВНО на
`marketState.closesAt`. Та же категория лага: между срабатыванием таймера
закрытия и строкой захвата снимка успевает пройти `await
cancelRestingIfAny(...)` (в LIVE — реальный сетевой запрос отмены ордера).

**Фикс.** Обе точки записи `priceAtClose` в `finalizeMarket` (ветка
`positioned` и ветка исполненной GTD-лимитки) теперь используют
`priceFeed.getPriceAt(assetPrefix, marketState.closesAt.getTime())` вместо
`getSnapshot()`. `atrAtClose` НЕ трогали — ATR это агрегат по закрытым
свечам (`computeAtr`), у него разрешение "целая свеча", точечный лаг в
секунды для него не имеет значения, там `getSnapshot().atr` как и раньше.

**Видимость в логах (явный запрос пользователя).** Лог открытия окна
(`"открыт WS-поток..."`) теперь показывает не только `referencePrice`, но и
лаг найденного тика от истинной границы окна в мс (когда `getPriceAt`
вернул значение) — чтобы точность референса была видна сразу в проде, а не
только при ручном сопоставлении со скриншотами Polymarket, как в Сессии 11.
Дополнительно: если найденный тик неожиданно далёк от границы
(`REFERENCE_LAG_WARN_MS`=3с, чисто информационный порог, ничего не
блокирует) — отдельный WARN о вероятной дыре в потоке трейдов рядом с
границей окна.

**Ответ на альтернативную схему пользователя** ("статично сохранять цену
открытия каждые 5 минут ±30с, первое окно после старта пропускать"): по
сути уже реализовано, но через ОБЩИЙ, более гибкий механизм — точечный
поиск по буферу сырых тиков (`getPriceAt`) вместо заранее вычисленного
статичного значения на фиксированную сетку границ:
- "Первое окно после старта пропускаем" — уже так и работает: если буфер не
  достаёт так далеко назад (только что подключились), `getPriceAt`
  возвращает `null`, гейт честно уходит в fail-closed для этого окна с явным
  WARN — функционально то же самое, что "пропустить", просто через общий
  fail-safe механизм, а не через отдельный список исключений.
- "Смотрим, какие тики ближе всего к цене открытия" — то же самое, что
  делает `getPriceAt`: ищет ближайший тик К ГРАНИЦЕ ПО ВРЕМЕНИ (не "по
  цене" — по времени, это и есть корректная постановка: нам нужна цена в
  момент времени X, а не тик с какой-то особой ценой).
- Разница с "статично сохранять раз в 5 минут": `getPriceAt` считает то же
  самое ПО ТРЕБОВАНИЮ, для любого произвольного timestamp в пределах
  `FEED_RECENT_TICKS_RETENTION_MS` — что позволило бесплатно переиспользовать
  ровно тот же механизм для ЗАКРЫТИЯ (эта сессия) без отдельной статичной
  структуры "открытие/закрытие" на каждое окно.

Покрыто тестом 14 в `verify-trading-logic.ts` (`priceAtClose` берётся из
`getPriceAt(closesAt)`, а не из `getSnapshot()`; `atrAtClose` по-прежнему
из `getSnapshot()`).

- Пользователь просит присылать изменения **полным архивом**, повторяющим
  структуру проекта — не патчами/диффами.
- `.env.example` присылать также отдельным файлом (помимо архива) — иначе
  дотфайл иногда "теряется" на его стороне после распаковки.
- Перед сдачей: `npx tsc --noEmit -p tsconfig.json` (чисто),
  `npx tsx scripts/verify-trading-logic.ts` (все тесты зелёные) и
  `npx tsx scripts/verify-price-feed.ts` (вотчдог фида, добавлен в Сессии 9) —
  обязательный минимум перед каждой правкой.
- Пользователь давал реальные логи/скриншоты неудачных попыток как
  основной способ находить баги — стоит и дальше воспринимать такие разборы
  как приоритет №1 (реальные деньги/капитал), а не как второстепенную
