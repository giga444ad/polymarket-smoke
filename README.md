# Polymarket 5m Bot — челлендж "500 шагов"

Автономный NestJS-бот для 5-минутных BTC up/down маркетов на Polymarket.
С момента старта каждого 5-минутного интервала держит открытый WebSocket
к обоим токенам (YES/NO) и весь интервал следит за стаканом в реальном
времени — а не только последние несколько секунд. Есть **смоук-режим**
(по умолчанию), где WS и вся логика работают по-настоящему, но ордера
только эмулируются, ничего не уходит на биржу.

## Стратегия (v2 — на WebSocket, два правила)

### Правило A — агрессивный маркет-тейк (не лимитка!)

Раньше ставилась лимитка по ¢99 и оставалась ждать — плохая идея: если
свеча резко идёт в одну сторону, предложений на продажу по ¢99 может
просто не быть, и лимитка никогда не исполнится. Теперь вместо этого:

- Весь интервал слушаем best ask обоих исходов через WS.
- Как только best ask любого из них попадает в
  `[MIN_MARKET_PRICE, MAX_MARKET_PRICE]` (по умолчанию **¢99–¢99.9**) —
  сразу шлём **FAK-ордер** (fill-and-kill, ближайший аналог "маркета" на
  Polymarket: берёт всё, что есть в стакане по цене не хуже потолка, а
  остаток биржа сама отменяет) с потолком `MAX_MARKET_PRICE`.
- Это и есть "цель — попасть по ¢99, но не пропустить сделку": если книга
  уже ушла на ¢99.3, а не ¢99.0 — всё равно берём, лишь бы не выше потолка.

### Правило B — лимитка-фолбэк (только когда продавцов реально нет)

Если у "фаворита" (исход с более высоким best bid) вообще нет ask дешевле
потолка — значит взять маркетом нечего, и вот тогда включается лимитка,
которая **переставляется** по мере приближения к закрытию:

| Условие | Цена лимитки |
|---|---|
| фаворит определился (`bestBid >= FAVORITE_BID_THRESHOLD`, по умолчанию ¢90), продавцов дешевле потолка нет, до закрытия > `LIMIT_TIER2_SECONDS` (по умолчанию 150с = 2.5 мин) | **T1 = ¢99** |
| то же, но до закрытия ≤ 150с и > `LIMIT_TIER3_SECONDS` (60с) | **T2 = ¢99.5** |
| до закрытия ≤ 60с | **T3 = ¢99.9** |

При смене тира старая лимитка сначала отменяется, потом ставится новая —
никогда не висят одновременно два ордера на один маркет. Ордер реальный —
`GTD` (good-till-date) с истечением ровно на закрытии маркета, так что
даже если бот не успеет сам её снять, биржа снимет её автоматически.

Итоговый фактический коридор входа — ровно тот, что вы просили:
**¢99–¢99.9** (маркет-тейк с одной стороны, лимитки-фолбэк с другой).

### Почему вообще возможны цены типа ¢99.5/¢99.9

Официально подтверждено (docs.polymarket.com/market-data/websocket/market-channel):
тик-сайз маркета **динамически меняется** — событие `tick_size_change`
прилетает, когда цена уходит выше 0.96 или ниже 0.04, и тик сужается с
0.01 до 0.001 (иногда 0.0001). Бот подписан на это событие и всегда
считает целевые цены по актуальному тик-сайзу конкретного момента
(`roundToTick`), а не по жёстко зашитому 0.01.

## Как читается стакан

WS-эндпоинт `wss://ws-subscriptions-clob.polymarket.com/ws/market`,
без авторизации. Подписка сразу на оба токена
(`{"type":"market","assets_ids":[...],"custom_feature_enabled":true}`),
дальше живём на событиях `book` (снапшот при подписке), `best_bid_ask` и
`price_change` (обновления лучшей цены) и `tick_size_change`. Раз в 10с
шлём сырую строку `"PING"`, сервер отвечает `"PONG"` — это тоже
по официальному протоколу, а не самодеятельность.

REST (`clob.polymarket.com/book`) используется только один раз при
старте каждого маркета — забрать официальный `min_order_size` (см. ниже)
и стартовый тик-сайз, до того как подключился WS.

## ВАЖНО: минимальный размер ордера биржи vs BET_AMOUNT

Polymarket считает минимальный размер ордера (`min_order_size`) на
уровне маркета — бот читает это значение **с самой биржи в реальном
времени**, ничего не захардкожено. По независимым источникам для этих
5-минутных BTC-маркетов минимум обычно около **5 токенов**, что при цене
~¢99 — это ~$4.95 нотионала. Если `BET_AMOUNT` меньше этого (например,
$1), почти каждая сделка будет упираться в минимум.

Бот **не тратит молча больше, чем вы просили**: если для выполнения
биржевого минимума нужно больше, чем `BET_AMOUNT * MAX_OVERSPEND_MULTIPLIER`
(по умолчанию x1.5), шаг просто пропускается с явным логом
("больше допустимого перерасхода"), вместо того чтобы тихо поставить
ставку в 5 раз больше задуманной. Если хотите, чтобы бот реально
торговал, а не пропускал почти всё — либо поднимите `BET_AMOUNT`
(по умолчанию уже стоит **5**, не 1 — на основе этого расчёта), либо
увеличьте `MAX_OVERSPEND_MULTIPLIER`.

## Прочитать перед боевым запуском (SMOKE_START=false)

GitHub-репозиторий `Polymarket/clob-client` (пакет, которым бот торгует)
на момент сборки помечен archived владельцем с пометкой "больше не
функционален", хотя `docs.polymarket.com/trading/quickstart` на тот же
момент всё ещё описывает установку именно этого пакета — источники
противоречат друг другу. Реальная торговля изолирована в одном файле
(`src/polymarket/polymarket-trader.service.ts`) и включается только при
`SMOKE_START=false`; WS-чтение стакана и вся логика шагов от этого файла
не зависят вообще. Перед боевым запуском без присмотра — прогоните
вручную один ордер и проверьте актуальное состояние SDK по ссылкам в
шапке файла.

**Дополнительный источник неопределённости для боевого режима**: у нас
нет подписки на приватный User-канал WS (там нужна авторизация), поэтому
для лимиток (Правило B) бот не узнаёт об исполнении мгновенно — он
проверяет фактический `size_matched` ордера через REST **в момент
закрытия маркета** (`getOrder`). Если ордер исполнился раньше — это
корректно определится постфактум; просто уведомление о самом факте
исполнения не приходит в реальном времени. Для маркет-тейка (Правило A)
эта проблема не стоит — там ответ на сам вызов ордера уже говорит,
исполнилось или нет.

## Установка и смоук-запуск

```bash
docker compose up -d postgres
npm install
cp .env.example .env
npm run start:dev
```

```bash
curl http://localhost:3000/health
curl http://localhost:3000/analytics/summary
curl "http://localhost:3000/analytics/logs?limit=200"
```

Статусы в `market_logs`: `pending_resolve` (ждём резолва Gamma),
`win`/`loss`, `skipped` (за весь интервал ни один исход не подошёл ни
под одно правило), `unfilled` (лимитка Правила B выставлялась, но так и
не исполнилась до закрытия), `error`.

### Локальная проверка без реальной сети

Два вспомогательных скрипта в `scripts/` (не часть самого приложения,
можно удалить):

```bash
npx tsx scripts/verify-ws-stream.ts       # поднимает локальный fake WS-сервер
                                           # по протоколу Polymarket и проверяет разбор
                                           # book/price_change/tick_size_change/PING-PONG
npx tsx scripts/verify-trading-logic.ts   # прогоняет Правило A/B на фейковых
                                           # зависимостях: пороги входа, переходы
                                           # тиров T1->T2->T3, идемпотентность лога
```

## Переход в боевой режим

1. `.env`: `PRIVATE_KEY`, `SIGNATURE_TYPE` (0 для обычного MetaMask-кошелька
   с MATIC на газ и USDC.e на балансе; 1/2 — email-логин/встроенный кошелёк
   Polymarket.com, тогда нужен `FUNDER_ADDRESS` — ваш Polymarket Profile
   Address).
2. По желанию `POLY_API_KEY`/`POLY_SECRET`/`POLY_PASSPHRASE` (иначе бот сам
   вызовет `createOrDeriveApiKey`).
3. `SMOKE_START=false`.
4. Если боевой клиент не поднимется — бот сам откатится в смоук и громко
   залогирует причину.

## Структура проекта

```
src/
  entities/
    attempt.entity.ts            # серия шагов (сброс на проигрыше)
    market-log.entity.ts         # терминальная запись по каждому 5м-маркету
  polymarket/
    gamma-market.service.ts      # поиск маркета по slug + резолв исхода (Gamma REST)
    clob-public.service.ts       # разовый REST-бутстрап (min_order_size, tick_size)
    market-ws-stream.ts          # live WS-стакан на весь интервал (Правила A/B читают отсюда)
    polymarket-trader.service.ts # боевая отправка ордеров (ИЗОЛИРОВАНО, см. warning выше)
  trading/
    trading.service.ts           # обнаружение маркета, Правило A/B, финализация, резолвер
    trading.module.ts
  analytics/
    analytics.controller.ts      # /analytics/summary, /analytics/logs
    health.controller.ts         # /health
  app.module.ts
  main.ts
scripts/
  verify-ws-stream.ts            # локальная проверка разбора WS-протокола
  verify-trading-logic.ts        # локальная проверка Правил A/B на фейках
```

## Известные ограничения

- `synchronize: true` удобен для смоука; для долгого боевого прогона
  лучше завести явные TypeORM-миграции.
- Резолвер побед/поражений остаётся REST-опросом Gamma API (не WS)
  — надёжный и простой источник истины по исходу, задержка до
  `RESOLVE_POLL_INTERVAL_MS` не критична, ведь сами сделки уже сделаны.
- Комиссии/сlippage не учитываются в определении "выигрыша" — фиксируется
  только совпадение выбранного исхода с резолвом рынка, не итоговый PnL.
- Один WS-коннект на активный маркет; при обрыве связи — автопереподключение
  с бэкоффом и повторной подпиской (см. `MarketWsStream`).
