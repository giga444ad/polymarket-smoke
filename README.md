# Polymarket 5m Bot — челлендж "500 шагов"

Автономный NestJS-бот для 5-минутных BTC up/down маркетов на Polymarket:
за секунды до закрытия свечи покупает исход, чей `ask` находится в узком
ценовом коридоре (по умолчанию ¢98–¢99), на фиксированную сумму ($1),
и ведёт счёт побед подряд (шагов) в Postgres. Может работать без
присмотра всю ночь, включая **смоук-режим**, где ордера не отправляются
на биржу — только эмулируются и проверяются на "выиграл бы / нет".

Идея не про мат.ожидание, а про попытку дойти до цели (по умолчанию 500
шагов). Один проигрыш = попытка заканчивается, счётчик уходит в новую
попытку.

## Прочитать перед запуском (важно)

На момент сборки этого проекта (сентябрь 2026) в экосистеме
Polymarket-SDK — путаница:

- GitHub-репозиторий `Polymarket/clob-client` (пакет `@polymarket/clob-client`,
  которым бот торгует по умолчанию) **архивирован владельцем** с явной
  припиской: *"The client is no longer functional and should not be used
  for new or existing integrations"*, и рекомендацией переходить на новый
  унифицированный `@polymarket/client`.
- При этом официальная страница `docs.polymarket.com/trading/quickstart`
  на тот же момент всё ещё описывает установку и использование именно
  старого `@polymarket/clob-client` — то есть сами официальные источники
  друг другу противоречат.
- Новый `@polymarket/client` имеет статус **beta**, его API ещё меняется.

Из-за этого вся боевая отправка ордеров изолирована в одном файле —
`src/polymarket/polymarket-trader.service.ts` — и включается **только**
при `SMOKE_START=false`. Смоук-режим (то, что нужно на сегодня-ночью)
этот файл вообще не трогает: он ходит напрямую в публичный
`GET https://clob.polymarket.com/book` (без авторизации) и в публичный
Gamma API — оба этих REST-эндпоинта стабильны и не зависят от того,
жив npm-пакет или нет.

**Перед тем как ставить `SMOKE_START=false` и уходить спать:**
1. Проверьте актуальное состояние на
   https://docs.polymarket.com/trading/quickstart и
   https://github.com/Polymarket/ts-sdk — возможно, к моменту чтения
   картина снова поменяется.
2. Сделайте один ручной раунд (один ордер маленького размера) и
   убедитесь, что он реально исполнился и виден в личном кабинете —
   до того, как оставлять бота автономным на всю ночь.
3. Устанавливайте зависимости только из официального scope `@polymarket/*`.
   В нише вокруг Polymarket-ботов уже фиксировались вредоносные пакеты,
   маскирующиеся под официальные (например, под видом "Kelly-criterion
   sizing helper", который на самом деле скачивал и исполнял чужой код
   при `npm install`). Не добавляйте сторонние "обёртки" без проверки.

## Стратегия (как реализовано)

1. Каждые 5 минут вычисляется slug текущего интервала:
   `btc-updown-5m-{unix-таймстамп-закрытия}` (например
   `btc-updown-5m-1788724500`).
2. Маркет ищется через `GET gamma-api.polymarket.com/events?slug=...`
   (именно `/events`, а не `/markets` — вторые эти маркеты фильтруют).
3. Пока до закрытия больше ~10 секунд — редкий опрос (по умолчанию раз
   в 2с), чтобы не спамить API.
4. В последние `SECONDS_BEFORE_CLOSE` секунд (по умолчанию 3) — плотный
   опрос стакана обоих токенов (`YES`/`NO`) через публичный
   `GET clob.polymarket.com/book?token_id=...`.
5. Если у одного из исходов лучший `ask` попадает в
   `[MIN_ENTRY_PRICE, MAX_ENTRY_PRICE]` **и** в стакане реально есть
   объём хотя бы на `BET_AMOUNT` — это кандидат. Если подходят оба
   исхода, берётся тот, что ближе к верхней границе (более "уверенный").
6. Смоук: в БД пишется симулированная покупка `status=pending_resolve`,
   на биржу ничего не уходит. Боевой режим: отправляется `FOK`-ордер
   (fill-or-kill — либо исполняется целиком сразу, либо биржа сама его
   отменяет) через `@polymarket/clob-client`.
7. Если ни один исход не подошёл — шаг помечается как `skipped`, но
   запись в БД всё равно есть (чтобы утром видеть полную картину, а не
   только успешные попытки).
8. Отдельный фоновый цикл (резолвер) раз в 10 секунд проверяет закрытые
   маркеты через Gamma API (`outcomePrices`) и:
   - при выигрыше — `currentStep += 1` у текущей попытки; при достижении
     `TARGET_STEPS` попытка помечается `completed_target`;
   - при проигрыше — попытка помечается `failed`, тут же создаётся новая
     попытка (`attemptNumber + 1`) с шагом 0.

Смоук и боевой режимы ведут отдельные, не пересекающиеся серии попыток
(`isSmoke` в таблице `attempts`), поэтому ночной смоук-прогон не портит
статистику будущего боевого прогона и наоборот.

## Стек

- Node.js 22, NestJS 11, TypeScript (CommonJS — стабильнее с
  `emitDecoratorMetadata`/TypeORM, чем свежий ESM-шаблон Nest CLI).
- TypeORM 0.3 + PostgreSQL (`synchronize` включён по умолчанию для
  быстрого смоук-старта; для боевого продакшена лучше завести обычные
  миграции — см. `TYPEORM_SYNC=false` в `.env.example`).
- `axios` — для Gamma API и публичного REST-стакана CLOB.
- `@polymarket/clob-client` + `ethers@5` — только для боевой отправки
  ордеров, изолированно (см. предупреждение выше).

## Установка и смоук-запуск на сегодня

```bash
# 1. Postgres (или используйте свой, тогда пропустите этот шаг)
docker compose up -d postgres

# 2. Зависимости (Node 22)
npm install

# 3. Конфиг
cp .env.example .env
# SMOKE_START=true уже стоит по умолчанию — можно не трогать .env вообще,
# кроме POSTGRES_* если Postgres не через docker-compose.

# 4. Запуск
npm run start:dev
```

Проверить, что бот жив:

```bash
curl http://localhost:3000/health
curl http://localhost:3000/analytics/summary
```

Логи в консоли покажут `[Skip]` на маркетах вне коридора цены и
`[SMOKE]` на тех, где условие выполнилось. Через `RESOLVE_POLL_INTERVAL_MS`
после закрытия каждого маркета в логах появится результат резолва
(`win`/`loss`) и обновлённый шаг попытки.

Утром:

```bash
curl http://localhost:3000/analytics/summary   # сводка по попыткам
curl http://localhost:3000/analytics/logs?limit=200   # сырые логи по маркетам
curl "http://localhost:3000/analytics/logs?status=win"
```

## Переход в боевой режим

1. Заполните в `.env`: `PRIVATE_KEY`, `SIGNATURE_TYPE` (0, если это
   обычный кошелёк MetaMask с MATIC на газ и USDC.e на балансе; 1/2 —
   если торгуете через email-логин/встроенный кошелёк Polymarket.com,
   тогда нужен `FUNDER_ADDRESS` — это ваш Polymarket Profile Address,
   куда заведён USDC).
2. При желании — `POLY_API_KEY`/`POLY_SECRET`/`POLY_PASSPHRASE` (иначе
   бот сам вызовет `createOrDeriveApiKey` при старте).
3. `SMOKE_START=false`.
4. Если боевой клиент не проинициализируется (например, из-за
   нерабочего SDK — см. предупреждение выше), бот **сам** откатится в
   смоук-режим и громко залогирует причину — деньги случайно не потратит.

## Структура проекта

```
src/
  entities/
    attempt.entity.ts        # серия шагов (сбрасывается на проигрыше)
    market-log.entity.ts     # запись по каждому обработанному 5м-маркету
  polymarket/
    gamma-market.service.ts      # поиск текущего маркета + резолв исхода (Gamma API)
    clob-public.service.ts       # публичный стакан (без авторизации)
    polymarket-trader.service.ts # боевая отправка ордеров (ИЗОЛИРОВАНО, см. warning выше)
  trading/
    trading.service.ts       # основной цикл + резолвер
    trading.module.ts
  analytics/
    analytics.controller.ts  # /analytics/summary, /analytics/logs
    health.controller.ts     # /health
  app.module.ts
  main.ts
```

## Известные ограничения / что стоит доделать перед долгим боевым прогоном

- `synchronize: true` удобен для смоука, но для прода лучше явные
  миграции TypeORM (риск случайного дропа/пересоздания колонок при
  правках сущностей).
- Нет ретраев/backoff для одиночных сетевых сбоев внутри `evaluateAndAct`
  (если Gamma/CLOB моргнули ровно в момент входа — шаг будет пропущен,
  а не переотправлен; это осознанный выбор в пользу простоты и
  предсказуемости для смоука, а не баг).
- Комиссии/slippage/газ не учитываются в расчёте "выигрыша" — в БД
  фиксируется только исход рынка (угадали/нет), не итоговый PnL.
- Резолвер полагается на `outcomePrices` из Gamma API; если оракул
  резолвит маркет с задержкой, запись повиснет в `pending_resolve` до
  следующего опроса — это нормально.
