# Polymarket 5m Bot — челлендж "500 шагов"

Автономный NestJS-бот для 5-минутных up/down маркетов на Polymarket (можно
вести несколько монет параллельно). С момента старта каждого 5-минутного
интервала держит открытый WebSocket к обоим токенам (YES/NO) и весь
интервал следит за **полным стаканом** в реальном времени — не только
top-of-book. Есть **смоук-режим** (по умолчанию), где WS и вся логика
работают по-настоящему, но ордера только эмулируются — причём максимально
честно, проходом по реальным уровням стакана, а не по одной "лучшей" цене.

## v3: честная эмуляция исполнения (VWAP по стакану)

Раньше смоук считал, что вся сделка прошла по единственной лучшей цене —
это создавало иллюзию, что "купили по ¢99.00" вообще всегда, и не защищало
от дребезга: тонкая одиночная заявка на секунду повисает по ¢99 с мизерным
объёмом с "невыигрышной" стороны, бот её хватает как сигнал, а через
секунду настоящие деньги идут в другую сторону.

Теперь `src/polymarket/market-ws-stream.ts` держит **полный локальный
стакан** (все уровни цены, не только лучший) — обновляется по `book`
(снапшот) и `price_change` (точечные правки уровня, `size=0` = уровень
снят). А `src/polymarket/book-fill.util.ts` (`walkAsksForFill`) реально
проходит по уровням от самой дешёвой цены вверх, не заходя выше
`MAX_MARKET_PRICE`, — ровно так же, как исполнился бы настоящий FAK-ордер:

```
asks: [{0.99, 40 шт}, {0.995, 2 шт}, {0.998, 15 шт}]
заявка $42 → берём все 40 шт по 0.99 (=$39.6), остаток $2.4 добираем
по 0.995 (~2.41 шт) → средняя цена входа НЕ ровно 0.99, а VWAP чуть выше.
```

Дальше два фильтра защиты от дребезга:

- **`MIN_FILL_RATIO`** (по умолчанию 0.5) — если реальной глубины хватает
  меньше чем на половину заявленной ставки, это, скорее всего, тонкая
  одиночная заявка-шум, а не настоящий сигнал — шаг пропускается целиком,
  а не открывается на 5% от задуманного объёма.
- Проверка **`minOrderSize`** теперь идёт по фактически исполнимому
  объёму (`filledShares`), а не по номинальной ставке.

Для Правила B (лимитка-фолбэк) — то же самое зеркально: наша резюм-лимитка
считается исполненной не по "касанию" лучшего ask нашей ценой, а когда
**накопленный объём продавцов** по нашей цене или ниже (`cumulativeUsdAtOrBelow`)
реально перекрывает нашу целевую сумму. Цена исполнения при этом — наша
собственная лимитная цена (гарантия лимитного ордера), а не VWAP чужого
прохода.

## Стратегия (Правило A / Правило B)

### Окно входа — не входим раньше последней минуты

**Реальный инцидент**: оба зафиксированных слива на eth-updown-5m случились
на входах за 2-3 минуты до закрытия — маркетмейкер уже давал ¢99, но рынок
ещё не "определился" с направлением, и цена успевала развернуться до
резолва. Чем раньше вход, тем рискованнее сделка при прочих равных.

Поэтому ни Правило A, ни Правило B теперь вообще не пытаются войти, пока не
останется `LAST_ENTRY_WINDOW_SEC` секунд до закрытия (по умолчанию **60**).
До этого момента бот просто наблюдает за стаканом и ничего не делает —
считаем, что упустить шаг лучше, чем взять его слишком рано. Как только
окно наступает, начинают действовать оба правила ниже как обычно.

### Правило A — агрессивный маркет-тейк (не лимитка!)

- Внутри окна входа слушаем полный стакан обоих исходов через WS.
- Как только best ask любого из них попадает в
  `[MIN_MARKET_PRICE, MAX_MARKET_PRICE]` (по умолчанию **¢99–¢99.9**) —
  проходим по стакану (VWAP, см. выше) и, если реального объёма хватает
  (`MIN_FILL_RATIO`), шлём **FAK-ордер** с потолком `MAX_MARKET_PRICE`.
- Живая биржа исполняет FAK точно так же (берёт всё по цене не хуже
  потолка, остаток отменяет сама) — смоук с VWAP-проходом максимально
  близко повторяет это поведение локально.

### Правило B — лимитка-фолбэк (только когда продавцов реально нет)

Если у "фаворита" (исход с более высоким best bid, `FAVORITE_BID_THRESHOLD`)
вообще нет ask дешевле потолка — внутри окна входа включается лимитка,
которая **переставляется** по мере приближения к закрытию:

| Условие | Цена лимитки |
|---|---|
| фаворит определился, продавцов дешевле потолка нет, до закрытия > `LIMIT_TIER2_SECONDS` (40с) | **T1 = ¢99** |
| то же, но до закрытия ≤ 40с и > `LIMIT_TIER3_SECONDS` (15с) | **T2 = ¢99.5** |
| до закрытия ≤ 15с | **T3 = ¢99.9** |

Тиры подразумевают, что `LIMIT_TIER2_SECONDS`/`LIMIT_TIER3_SECONDS` **не
больше** `LAST_ENTRY_WINDOW_SEC` — иначе T1/T2 недостижимы (окно входа само
по себе наступит раньше их порога).

При смене тира старая лимитка сначала отменяется, потом ставится новая.
Реальный ордер — `GTD` с истечением на закрытии маркета.

Если очередной тир не проходит по минимуму биржи/бюджету — это
**запоминается** (`skippedLimitTier`) и не пере-проверяется на каждом
WS-тике, пока не сменится тир или не поменяется цена фаворита. Раньше
это была причина спама в логах: одна и та же проверка "не хватает
объёма" писалась в лог на каждое обновление стакана (по многу раз в
секунду) — теперь пишется один раз на тир.

Цены типа ¢99.5/¢99.9 возможны потому, что тик-сайз Polymarket динамически
сужается с 0.01 до 0.001, когда цена уходит выше 0.96 (`tick_size_change`,
подтверждено официальной документацией) — бот подписан на это событие и
всегда считает целевые цены по актуальному тик-сайзу момента.

### ATR-гейт — теперь включён по умолчанию, и fail-closed

Раньше `ENTRY_FILTER_ENABLED=false` (SHADOW-режим: диагностика считалась,
но не блокировала вход) — стратегия была "накопим статистику, потом
включим". Статистика накоплена на реальных сливах, и приоритет сместился
на сохранение капитала: **лучше пропустить сделку, чем потерять депозит**.
Теперь по умолчанию:

- `ENTRY_FILTER_ENABLED=true` — вход блокируется, если дистанция цены от
  референса окна меньше `MIN_DISTANCE_ATR_RATIO` (по умолчанию 1.5x) ATR —
  то есть похоже на болтанку у границы, а не уверенное движение.
- Если диагностика недоступна (внешний фид не отдал ни одного тика к
  моменту входа — напр. WS Binance/Bybit недоступны) — **раньше это было
  fail-open** (пропускали проверку, входили не глядя), **теперь fail-closed**
  (шаг пропускается целиком). Если фид ляжет надолго — бот будет пропускать
  шаги, а не торговать вслепую; это ожидаемое поведение при этой настройке,
  не баг.

## Независимые потоки (актив × таймфрейм) и реинвест-прогрессия

Раньше был один общий счётчик шагов на все активы (`MARKET_ASSETS`,
через запятую) и одна плоская ставка (`BET_AMOUNT`). Теперь это заменено на
`STREAMS_CONFIG` — JSON-массив, где каждый элемент описывает полностью
независимый поток: свой `Attempt`, свой прогресс, своя прогрессия стейка.

```json
STREAMS_CONFIG=[
  {"streamKey":"btc-updown-5m","kind":"interval","intervalSec":300,"slugPrefix":"btc-updown-5m","baseStake":5},
  {"streamKey":"btc-updown-15m","kind":"interval","intervalSec":900,"slugPrefix":"btc-updown-15m","baseStake":5},
  {"streamKey":"bitcoin-up-or-down","kind":"hourly-et","intervalSec":3600,"etSlugBase":"bitcoin-up-or-down","baseStake":5}
]
```

- **`kind: "interval"`** (5m/15m) — слаг маркета = `${slugPrefix}-${unix_start}`,
  напр. `btc-updown-5m-1788998100`. Таймстамп — начало интервала.
- **`kind: "hourly-et"`** (1h) — слаг СОВЕРШЕННО другого формата, календарная
  строка по America/New_York: `bitcoin-up-or-down-september-9-2026-7pm-et`
  (месяц словом, день/год числом без нулей, час 1-12 + am/pm, суффикс `-et`).
  Оба формата проверены вручную на живых слагах Polymarket перед реализацией.
  Граница часа при этом одна и та же что по UTC, что по ET (оффсет — целое
  число часов), так что арифметика начала/конца интервала общая — отличается
  только СТРОКА слага, не момент времени.
- 4ч/1д сознательно не подключены (см. ниже "3×500 по таймфреймам").

Каждый поток ведёт свой `Attempt` (`streamKey` в таблице `attempts`) —
выигрыш/проигрыш на одном потоке больше не трогает прогресс другого.
`/analytics/summary` даёт `bestByStream` (лучшая попытка по каждому потоку
отдельно) в дополнение к `byAsset` (статистика побед/поражений/профита).

### Реинвест-прогрессия ставки

`Attempt.currentStake` — это НЕ константа: на старте попытки равен
`baseStake` потока, а после каждого выигрыша пересчитывается как
`filledAmount / entryPrice` ЭТОГО выигранного шага — то есть от реально
полученной по факту исполнения суммы (VWAP гуляет по тирам лимитки/маркет-
тейка, поэтому и берём фактическую цену исполнения, а не константу ¢99).
При проигрыше открывается новая попытка того же потока с `currentStake`,
сброшенным обратно на `baseStake`.

Стейк каждого конкретного окна снимается ("замораживается") с
`Attempt.currentStake` в момент ОТКРЫТИЯ этого окна — в течение всего окна
используется именно это число, независимо от того, что происходит с
другими (не связанными) потоками параллельно.

### Замер глубины стакана перед доверием к цели "500 подряд"

На 500 шагах реинвеста стейк вырастает на несколько порядков от базового —
раньше или позже это упрётся в реальную глубину книги на ¢99+, а не в
проигрыш. Прежде чем полагаться на "500" как достижимую цифру, стоит
собрать статистику реальной глубины:

```
npx tsx scripts/measure-book-depth.ts
```

Отдельный долгоживущий процесс (не часть приложения), опрашивает стакан по
всем настроенным `STREAMS_CONFIG` каждые `DEPTH_POLL_MS` (по умолчанию 5с) и
пишет JSONL в `DEPTH_LOG_FILE` (по умолчанию `./book-depth-log.jsonl`):
таймстамп, поток, слаг, сколько $ доступно у фаворита по цене `¢99+`
(порог — `DEPTH_MIN_PRICE`). Разбор — вручную (`jq`/pandas/что удобно), сам
скрипт только копит данные, ничего не решает за вас.

### Приоритизация таймфреймов ("3×500 подряд")

5m/15m/1h оставлены как основные кандидаты на боевой критерий готовности —
у каждого разумное время набора чистой серии (см. обсуждение в BACKLOG.md).
4ч/1д сознательно исключены: набрать 500 подряд без единого сбоя на них
физически заняло бы месяцы-годы, и они непригодны как критерий готовности к
лайву в разумные сроки. Above-маркеты — отдельный трек с принципиально
другим критерием готовности (не streak, а статзначимое превышение winrate
над рыночной вероятностью) и в текущей реализации не затронуты.

## Профит и банкролл

Каждая запись в `market_logs` после резолва получает `profit` (в
долларах): на выигрыше — `filledAmount/entryPrice*(1-entryPrice)`
(столько заплатили за токен, столько же и заработали сверху при
погашении по $1), на проигрыше — `-filledAmount` (потеряна вся реально
вложенная сумма; `filledAmount` может быть меньше `betAmount`, если
глубины на полную ставку не хватило). `filledAmount` — это то, что
реально "стоит на кону", а не заявленная цель.

`/analytics/summary` отдаёт:

```json
{
  "startingBankroll": 1000,
  "currentBankroll": { "smoke": 1023.4, "live": 1000 },
  "profit": { "smoke": 23.4, "live": 0 },
  "byAsset": [
    { "assetPrefix": "btc-updown-5m", "isSmoke": true, "wins": 12, "losses": 1, "profit": 18.2 }
  ],
  "bestByStream": [
    { "streamKey": "btc-updown-5m", "attemptNumber": 3, "isSmoke": true, "reachedStep": 42, "targetSteps": 500, "status": "active", "currentStake": 6.12 }
  ]
}
```

`startingBankroll` (`STARTING_BANKROLL` в `.env`) — чисто для отображения
("если бы начали с X, сейчас у вас было бы Y"), реальными деньгами в
смоуке не рискуем.

## Как читается стакан

WS-эндпоинт `wss://ws-subscriptions-clob.polymarket.com/ws/market`, без
авторизации. Подписка на оба токена
(`{"type":"market","assets_ids":[...],"custom_feature_enabled":true}`),
живём на `book` (полный снапшот при подписке), `price_change` (точечные
изменения уровня) и `tick_size_change`. Раз в 10с шлём сырую строку
`"PING"`, сервер отвечает `"PONG"`.

REST (`clob.polymarket.com/book`) используется только один раз при старте
каждого маркета — забрать официальный `min_order_size` и стартовый
тик-сайз, до того как подключился WS.

## ВАЖНО: минимальный размер ордера биржи vs стейк шага

Минимум обычно около **5 токенов**, что при цене ~¢99 — это ~$4.95
нотионала. Бот не тратит молча больше, чем `(currentStake потока на этот
шаг) * MAX_OVERSPEND_MULTIPLIER` (по умолчанию x1.5) — если для минимума
биржи нужно больше, шаг просто пропускается с явным логом. При
`baseStake=1` это будет происходить почти всегда — поэтому дефолт на поток
стоит **5** (см. `STREAMS_CONFIG`).

## Прочитать перед боевым запуском (SMOKE_START=false)

GitHub-репозиторий `Polymarket/clob-client` (пакет, которым бот торгует)
на момент сборки помечен archived владельцем с пометкой "больше не
функционален", хотя `docs.polymarket.com/trading/quickstart` на тот же
момент всё ещё описывает установку именно этого пакета — источники
противоречат друг другу. Реальная торговля изолирована в одном файле
(`src/polymarket/polymarket-trader.service.ts`) и включается только при
`SMOKE_START=false`; WS-чтение стакана и вся логика шагов от этого файла
не зависят вообще. Перед боевым запуском без присмотра — прогоните
вручную один ордер и проверьте актуальное состояние SDK.

Для лимиток (Правило B) в боевом режиме нет подписки на приватный
User-канал WS (там нужна авторизация), поэтому бот не узнаёт об
исполнении мгновенно — проверяет фактический `size_matched` через REST
(`getOrder`) в момент закрытия маркета. Для маркет-тейка (Правило A) эта
проблема не стоит — ответ на сам вызов ордера уже говорит, исполнилось
или нет.

```bash
npm run start:dev
```

```bash
curl http://localhost:3000/health

curl "http://localhost:3000/analytics/logs?limit=200"
```

Статусы в `market_logs`: `pending_resolve`, `win`/`loss`, `skipped` (за
интервал ни один исход не подошёл ни под одно правило), `unfilled`
(лимитка выставлялась, но не набрала достаточный объём/не исполнилась до
закрытия), `error`.

### Локальная проверка без реальной сети

```bash
npx tsx scripts/verify-ws-stream.ts       # локальный fake WS-сервер по протоколу
                                           # Polymarket: book/price_change/tick_size_change/PING-PONG,
                                           # включая снятие уровня (size=0) и переход best ask
npx tsx scripts/verify-trading-logic.ts   # 8 проверок на фейках: дребезг НЕ покупается,
                                           # VWAP по нескольким уровням, потолок цены,
                                           # лимитка не исполняется по "касанию" (только по
                                           # накопленному объёму), антиспам тиров, профит
                                           # win/loss считается от filledAmount
```

**ВАЖНО про сборку**: в проекте обязательно должен быть `tsconfig.build.json`
(с `rootDir: "./src"` и `exclude: ["scripts", ...]`) — без него `nest build`
захватывает и `scripts/`, `rootDir` съезжает на корень проекта, и
`dist/main.js` уезжает в `dist/src/main.js` (`npm run start:prod` при этом
падает с `Cannot find module dist/main.js`). Если по какой-то причине этот
файл пропал — просто восстановите его в этом виде.

## Переход в боевой режим

1. `.env`: `PRIVATE_KEY`, `SIGNATURE_TYPE` (0 для обычного MetaMask-кошелька;
   1/2 — email-логин/встроенный кошелёк Polymarket.com, тогда нужен
   `FUNDER_ADDRESS`).
2. По желанию `POLY_API_KEY`/`POLY_SECRET`/`POLY_PASSPHRASE`.
3. `SMOKE_START=false`.
4. Если боевой клиент не поднимется — бот сам откатится в смоук и громко
   залогирует причину.

**Если приватный ключ когда-либо засветился где-то за пределами вашей
локальной машины (чат, скриншот, публичный репозиторий) — считайте его
скомпрометированным и переводите средства на новый кошелёк с новым ключом,
не полагаясь на то, что "никто не найдёт".**

## Известные ограничения

- `synchronize: true` удобен для смоука; для долгого боевого прогона лучше
  завести явные TypeORM-миграции.
- Резолвер побед/поражений — REST-опрос Gamma API (не WS), задержка до
  `RESOLVE_POLL_INTERVAL_MS` не критична, сделки уже сделаны к этому моменту.
- Комиссии/slippage сверх смоделированного VWAP не учитываются.
- Один WS-коннект на активный маркет на актив; при обрыве связи —
  автопереподключение с бэкоффом и повторной подпиской.
